# 装置 5 · 赛博开发者证件照（`app/`）

SpacemiT DevCon 2026 现场装置。参会者拍 1 张照片，K3 用 **RISC-V AI 核**做一次人像实例分割，
把人像抠出来做暗调强风格化，叠上 `#SpacemiTDevCon` 水印与 `SM-YYYY-NNNN` 编号，
出图并给一个二维码，手机扫码取图。

一句话人机流程：**站进取景框 → 勾同意 → 按快门 → AI 核抠像（约 0.2 秒）→ 合成暗调证件照 → 扫码取图（可保存、可删除）。**

全过程在本机完成：不上云、**不做人脸识别、不做身份比对**；出图不依赖外网（只有手机扫码取图需要手机与 K3 在同一个局域网）；
照片只存在装置本机的数据目录里，保留 1 天（`retention_hours=24`）。取图链接在生成 24 小时后失效，服务每分钟清理过期照片及其派生图片、对应成片记录。

现场值守是**非技术同事**。出问题的应急动作看 `app/docs/现场故障处置.md`（症状 → 三步内能做的动作 → 找谁）。

## 一、四个界面

四个页面由同一个服务（端口 **8090**）提供，真机地址就是 `http://<K3 的局域网 IP>:8090`：

| URL | 页面 | 谁用 | 用途 |
|---|---|---|---|
| `/` | 拍摄位 | 参会者 + 值守同事 | 实时取景、选底版风格、填署名、勾选《拍摄告知》、按快门、看成片与二维码 |
| `/stage` | 算力视图（大屏） | 围观者 | 实时预览（左右镜像，成片不镜像）、人像掩码逐像素成形、本次真实推理耗时、EP / CPU 徽章、最近成片、指令集跑马灯 |
| `/operator` | 现场管理总览 | 值守同事 | 简明运行状态，以及排队、成片和风格管理入口 |
| `/p/<取图令牌>` | 取图页 | 参会者手机 | 大图、保存原图、复制分享文案、**删除我的照片** |

- 例：`http://192.0.2.10:8090/stage`、`http://192.0.2.10:8090/operator`、
  `http://192.0.2.10:8090/p/V3f2O3CT2bl_Yt8hov2LLQ`。
- **取图入口是「取图令牌」，不是编号**：每张照片拍摄时生成一个 22 位随机串
  （`store.Record.new_token()`，`secrets.token_urlsafe(16)` = 128 位）。
  编号 `SM-2026-0001` 是连号的、可枚举的，**只用来显示** —— 拿编号去取图、
  缩略图、二维码、元信息、删除，**一律 404**（`store.by_token()` 只认令牌）。
  理由：编号当入口，等于把"从 0001 数到 9999"变成全场照片的下载器。
- 二维码里编码的是 `<同一地址>/p/<令牌>`（地址取服务自己的局域网 IP，
  可用 `BOOTH_PUBLIC_HOST` 或操作员面板覆盖）。
- 取图页对任何路径都返回 200（页面自己再去问元信息）；照片被删除后页面仍能打开
  并显示「已删除」，但图片链接立即 404。

后台各项功能有独立页面，手机与桌面均可使用：

| URL | 功能 |
|---|---|
| `/operator` | 现场总览 |
| `/operator/queue` | 排队名单与取消排队 |
| `/operator/photos` | 最近成片、取图与删除 |
| `/operator/styles` | 风格新增、编辑、启停、设默认、复制、恢复历史与删除 |
| `/operator/settings` | 取图地址、统一生成模型与拍摄告知 |
| `/operator/system` | 设备状态、恢复与维护 |

风格删除需要确认；排队或处理中的风格暂不能删除、停用，至少保留一条启用风格。
删除默认风格时自动选择启用的替代项，已删除的预设不会在服务重启后恢复。
新增或复制的风格启用后即可供参与者选择。六款画法与人像模式独立：默认「写实版」，也可选择「Q版大头像」，像素风同样适用。
写实版保留原脸型、下颌与五官比例；Q版以头肩大头像呈现，保留本人的轮廓和关键特征，不生成全身小人。
六款风格、两种模式均做轻度风格化美颜：均匀肤色、弱化暂时瑕疵和疲态、提亮眼神、轻润唇色，保留原脸型和辨识度，不瘦下颌、不换脸、不改变年龄、不做塑料磨皮。
像素风写实版也偏可爱，以色彩、像素眼神高光和淡腮红表现，不放大眼睛或头部；Q版仍只按所选模式放大整体头部。
随机变化主要留给画法、光色和简约背景。仅西装革履专业风换西装，其余风格保留原衣服。
报名及直接拍摄接口接收 `portrait_mode`（`standard` / `chibi`），缺省为 `standard`；该选择贯穿排队、生成与成片记录。
自动拍摄倒计时默认 **8 秒**；`BOOTH_CAPTURE_COUNTDOWN_SECONDS` 可显式覆盖（例如设为 `3` 使用 3 秒）。服务端重复开始同一会话不会重置倒计时，归零只触发一次拍摄。
OK确认后，人像模型在倒计时期间异步加载，检测框只辅助取景；漏检、重复框和背景人物不会取消拍摄。相机失帧、拍摄授权撤回或主动取消仍会中止拍摄。
目录 v7 更新六款预设的画法说明与轻度美颜提示词，保留现场模型、尺寸、启停、默认项和历史；不会重新添加已删除风格。
以上是生成约束，不是人脸识别或相似度评分，真人成片是否足够像本人仍需现场对照验收。
修改风格无需重启；部署代码时需等队列及拍摄任务清空再重启服务，避免使排队凭据失效。

排障用到的其他接口（契约见 `docs/spec/系统规格-v2.md §4`）：

```

GET  /api/state                  全量状态（相机 / 推理 / 磁盘 / 计数 / link_base / share / 最近成片）
GET  /api/operator/config        取图页地址（公网域名）配置

DELETE /api/photo/<令牌>         参会者删除权入口 —— 令牌就是凭证，跟着链接走
```

## 二、一键启动（真机）

```bash
/usr/bin/python3 /opt/devcon/app/booth_server.py
```

| 项 | 值 |
|---|---|
| 代码 | `/opt/devcon/app` |
| 模型 | `/opt/devcon/assets/models` |
| 端口 | `8090`（`--port` 可改） |
| 监听地址 | `0.0.0.0`（`--host` 可改） |
| 数据目录 | `BOOTH_DATA`，默认 `<app>/data` → 真机 `/opt/devcon/app/data` |
| 解释器 | **必须 `/usr/bin/python3`**（Bianbu 系统自带 cv2 / onnxruntime / spacemit_ort） |

**不要用 venv**：riscv64 上没有 onnxruntime 的 venv 轮子，用 venv 的 python 起不来推理。
依赖是零 pip 安装的：只用标准库 + numpy + PIL + cv2 + onnxruntime。

服务起来时会自动做**启动自检 + 模型预热**（抓帧 → 掩码 → 检测各跑一遍），
把第一个参会者本来要付的冷启动代价先付掉（首帧约 1.2 s，热身后约 0.2 s）。

常用参数与后台运行：

```bash
# 换端口 / 换监听地址
/usr/bin/python3 /opt/devcon/app/booth_server.py --port 8090 --host 0.0.0.0

# 没有相机时用合成源（排障 / 演示，界面上会亮「MOCK 合成源」徽章）
/usr/bin/python3 /opt/devcon/app/booth_server.py --mock-camera

# 后台常驻（推荐）：systemd 单元已入库 app/deploy/devcon-booth.service
sudo install -m 0644 /opt/devcon/app/deploy/devcon-booth.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now devcon-booth
sudo systemctl status devcon-booth
journalctl -u devcon-booth -f

# 不想用 systemd 的话（临时 / 排障）
nohup /usr/bin/python3 /opt/devcon/app/booth_server.py >> /opt/devcon/app/booth.log 2>&1 &
```

单元里的关键取舍（写在单元文件注释里）：排在 `network-online.target` 之后是为了**先拿到局域网地址**
（否则二维码会指到 `127.0.0.1`）；`Restart=always` + `RestartSec=2` 让崩溃自动重启，
并且给 AI 核线程槽留出被内核回收的时间。

★ **停服务用普通结束信号**（前台 `Ctrl+C`，或 `pkill -f booth_server.py`），**不要 `kill -9`**。
推理进程被强杀会泄漏 TCM block，之后 AI 核会一直被显示占住（`app/infer/worker.py` 里的
`release_stale_tcm()` 就是为这种残留准备的）。

大屏（DP 输出，kiosk）：

```bash
chromium --kiosk --app=http://127.0.0.1:8090/stage
```

| `BOOTH_CAMERA_DEVICE` | 空 | 强制指定相机节点；默认按 by-id 找 DICOTA，路径不存在时再按内核设备名找一遍（避开 metadata 节点） |

| `BOOTH_SEG_MODEL` | `/opt/devcon/assets/models/yoloe-v8s-seg.dynq.onnx` | 人像分割模型（AI 核） |

| `BOOTH_EP_THREADS_SEG` | `4` | 分割模型申请的 AI 核线程数 |
| `BOOTH_EP_THREADS_DET` | `2` | 检测模型申请的 AI 核线程数 |
| `BOOTH_EP_THREADS` | `8,4,2,1` | 拿不到目标线程数时的降档阶梯 |
| `BOOTH_MATTE_MODEL` | `/opt/devcon/assets/models/modnet.onnx` | **抠像模型（固定走 CPU，见 §五「抠像」）** |
| `BOOTH_MATTE_FILL` | `0.80` | 裁切时人应占裁切画面的比例（≈ 人框外扩 1.25 倍；这个数是扫出来的，见 §五「抠像」） |

| `BOOTH_MATTE_DECON` | `1` | 软边去背景色污染（过渡带不再混进旧背景）；`0` 关掉 |
| `BOOTH_MATTE_DECON_R` | `3` | 去污染的邻域半径（成片尺度） |
| `BOOTH_MATTE_MAX_SIDE` | `0` | 抠像 alpha 回传时的最大边；**`0` = 原尺寸，不要调小**（见 §五「抠像」） |
| `BOOTH_KV_FEATHER` | `0.10,0.06,0.10,0.16` | 人像窗四周的柔化宽度（左/上/右/下，占窗口宽或高的比例）；全 `0` 关掉（见 §五「抠像」） |

### 打印机（当前默认关闭）

项目打印端口走 CUPS 的 `lp` / `lpstat`，不会在 booth_server 进程内加载图像推理库。Canon SELPHY CP1500 的接入步骤、纸张、验收和回滚见 `docs/佳能CP1500-K3接入与打印SOP.md`。

| 变量 | 默认 | 作用 |
|---|---|---|
| `BOOTH_PRINT_ENABLED` | `false` | 置为 `true` 才装配真实 CUPS 打印端口；设备验收前保持关闭 |
| `BOOTH_PRINT_BACKEND` | `cups` | 当前仅支持 `cups` |
| `BOOTH_PRINT_QUEUE` | 空 | CUPS 队列名，如 `Canon_CP1500` |
| `BOOTH_PRINT_MEDIA` | 空 | 纸张选项；CP1500 验收后使用实际自报值，候选为 `Postcard.Borderless` |
| `BOOTH_PRINT_TIMEOUT` | `30` | 单次调用 `lp` 的超时时间；不等于照片出纸时间 |

`BOOTH_PRINTER_ENABLED` / `BOOTH_PRINTER_BACKEND` 是 auto_flow 严格配置中的打印门，当前 systemd 仍为 `false/none`。不要只改其中一组开关；真实打印必须在 CP1500 队列与首张样片验收通过后统一开启。

测试脚本自己的变量：`BOOTH_TEST_PORT`（`test_server.py`，默认 8099）、`BOOTH_E2E_PORT`（`e2e_test.py`，默认 8098）、`BOOTH_SHOOT_PORT`（`tools/shoot_ui.py`）。

## 四、怎么跑测试

这些脚本**不需要 pytest**，用标准库断言，直接跑，**退出码非 0 表示有 FAIL**。
输出里的 `SKIP` 是**如实降级**（AI 核被别的进程占着、相机没插、本机没有 cv2），**不是通过**。

```bash
cd /opt/devcon/app

# 二维码：纯 Python 独立解码器回环 + EC 边界（不依赖第三方库）
/usr/bin/python3 tests/test_qr.py

# 推理 worker：AI 核预算 / 哨兵协议 / 降级诚实性（约 40 s，会真加载模型）
/usr/bin/python3 tests/test_worker.py

# UVC 抓帧：by-id 解析 / 预览与拍照双分辨率 / 明确报错 / mock 降级
/usr/bin/python3 tests/test_camera.py

# 预览分发与掉线自愈：单生产者 / 多页面共享 / 掉线后自己接回来（不需要真相机）
/usr/bin/python3 tests/test_preview_hub.py

# 相机自愈的判定逻辑：连续读空 → 重开、冷却防抖、拍照降级（不需要真相机）
/usr/bin/python3 tests/test_camera_heal.py

# 抠像策略：先裁切后整幅的顺序、三道兜底、单路失败不拖垮（不需要真相机；
# 本机放了 modnet.onnx 时会连真模型一起冒烟）
```

### 抓帧进程与推理进程为什么必须分开

这不是风格选择，是**崩溃与不崩溃的区别**（`docs/spec/系统规格-v2.md §1.1`，来源为 yolos-box 的实测注释）：

- **`cv2` 与 `spacemit_ort` 不得同进程** —— OpenCV 的共享库栈会破坏 ORT 的日志管理器（import-order 崩溃）。
- **`onnxruntime` 必须先于 `spacemit_ort` 被 import** —— 反序直接报
  `Attempt to use DefaultLogger but none has been registered`。
- **EP 失败会往 stdout 打噪声** —— 一次冷启动实测能打出 48 行「EP Error …」，会把行式 JSON 协议冲碎，
  所以响应行必须带 `@@J ` 哨兵前缀，客户端丢弃所有不带前缀的行。

于是：`camera.py` 是**唯一** import cv2 的模块，`infer/worker.py` 是**唯一** import spacemit_ort 的模块，
两者用子进程 + 一行一个 JSON 通信。

### AI 核预算（8 个线程槽，最容易被抢）

| 事实 | 数值 |
|---|---|
| 全板 AI 核线程槽总数 | **8** |
| 会话占用方式 | 进程内多个 EP 会话**共享**这个池子，会话一旦创建**直到退出都占着** |
| 申请超量时 | EP 报 `Not enough available AI cores` 并**静默退回 CPU**（不报错） |
| 默认分配 | 分割 4 线程、检测 2 线程（留 2 槽余量）、文本编码器固定走 CPU |
| **抠像模型（MODNet）** | **固定走 CPU，一个槽都不占** —— 上 EP 会让进程硬崩，见下 |

**复核机制**：会话创建后用 `session.get_providers()` 复核是否真拿到 EP；拿不到就逐级降档，
最后退 CPU，并在 `/api/state`、大屏与操作员面板上**如实标注**（界面上写 `CPU` 就是真的在 CPU 上跑）。

可对外引用的真机实测数字（来源 `docs/需求原文.md §2.2`、`docs/spec/系统规格-v2.md §1.2`）：

- 同一台 K3 上，**量化（INT8）模型**走 AI 核相对 CPU 加速 **5.7×–67×**
  （人像分割 205 ms vs 1160 ms ≈ 5.7×；官方 demo 的 yolov8n/s 达到 49× / 67×）。
- **未量化的 FP32 模型几乎不加速**（1.0×–1.8×）——所以现场必须用量化模型。
- 全板 AI 核线程槽 **8 个**，别的进程（例如占着 8080 端口的 yolos-box）会先把核抢走。

### 预览：一路抓、N 路发，掉线自己接回来

大屏（`/stage`）和拍摄位（`/`）会**同时**拉 `/api/preview.mjpg`。早期每个连接各自
`mjpg_stream(camera, ...)` —— 两个页面 = 两个线程读同一个 V4L2 句柄、各自编一份 JPEG，
帧被轮流吃掉，两边都卡；CPU 还编了两份。现场看着就是「老是断流」。

现在只有一条抓帧线程（`camera.PreviewHub`）：抓一次、编一次、N 个连接只订阅结果。
新连接**立刻**拿到最近一帧（不用等下一个周期），慢连接只发最新的（自动丢帧），
所以页面开多少都不会把相机拖垮。

另一半是**掉线自愈**。相机是 USB 设备，链路一抖就会重新枚举，`/dev/videoN` 换号，
进程手里那条 fd 指向的是「已删除」的旧节点 —— 这时 `read()` 恒返回 False，
**重试多少次都没用**（现场实测：18:28 相机连掉两次，预览流死在那一刻，只能重启服务）。
所以：

- 连续 3 次读不到帧 → `Camera.recover()`：关掉、按 by-id 重新解析、重开（6 s 冷却，别把重连打成风暴）；
- 拍照要切分辨率，这一步最容易撞上链路抖动 → 失败先自愈重试，仍失败就用当前分辨率出图，
  并**如实**在 `degraded` 里标出来（宁可少几个像素，也不能让参会者空手离开）；
- 拍照分辨率默认 `1920x1080`：MJPG 2592x1944@30 要 30~60 MB/s，而这条 USB2 链路实际只有
  ~35 MB/s，一档就顶穿 → URB 溢出 → 设备重新枚举。成片真正用得上的人像窗只有约 278x357。
- 前端 `watchStream()` 每 4 秒给画面拍一次指纹，发现「没帧」或「画面卡住」就重连，
  并在取景区显示「相机重连中…」——**画面停了却什么都不说**，现场的人只会以为是相机坏了在干等。

现场排断流就看 `/api/state` 的 `preview`：

```json
{"clients": 2, "seq": 1542, "last_frame_s": 0.1, "last_error": null,
 "camera": {"device": "/dev/v4l/by-id/usb-...DICOTA-...-video-index0", "reopens": 0,
            "last_ok_s": 0.1, "fail_streak": 0, "snapshot_note": null}}
```

`clients` 意外归零 = 客户端没连上；`seq` 不涨 = 服务端没出帧（看 `last_error`）；
`reopens` 在涨 = 相机侧掉线过、进程内已经自愈；`last_frame_s` 一直涨 = 连自愈都没救回来。

### 取图页的公网地址（分享用）

现场默认是局域网 IP（`http://192.0.2.10:8090`）。但**明文 HTTP 的 IP 不是"安全上下文"** ——
实测 `isSecureContext=false`，于是 `navigator.share` / `navigator.clipboard` 全是
`undefined`：取图页上「分享」这类按钮在手机上点了等于没点。

挂一个公网 HTTPS 域名（K3 走隧道，照片不出机，见 `docs/06` §3.5）之后，
`navigator.share({files})` 可用 → 弹**系统分享面板** → 面板里直接有小红书 / 微信，
点进去就是发布页。这是唯一能真正跳到发布页的通道。

| 项 | 在哪 |
|---|---|
| 填地址 | 操作员面板 →「取图页地址（分享用）」→ 保存；留空 = 回落局域网 |
| 存到哪 | `data/settings.json`（**不在代码目录**：换域名、回滚配置都不该动代码） |
| 优先级 | 面板 > `BOOTH_PUBLIC_HOST` 环境变量 > 局域网 IP；面板上如实标来源 |
| 改完必须做的事 | **清二维码缓存** —— 二维码是按地址画好的 PNG，文件在就直读。不清就是"面板显示新域名、发出去的码指向旧地址"，全程不报错（坑 25 的同一个病）。`set_public_config()` 里已经做了 |

**地址是校验过才存下去的。** `normalize_base()` 只收 `http(s)://主机[:端口]`，
并且**自己再卡一道主机名字符集** —— 因为 `urlparse` 对主机名极其宽容：
`http://hello world` 也能解析出 `netloc="hello world"`。这种字符串会让二维码照常生成、
现场照常发出去、扫开打不开，而**没有任何人会去查**（这个 bug 是真机抓出来的，见坑 28）。

**公网那一侧只放行** `/p/`、`/static/`、`/api/photo`、`/api/thumb`、`/api/photo-meta`。
`/api/state` 不能公开：它会把**最近成片的编号清单**、相机状态、磁盘余量一起吐出来。
取图页要的那一点点信息由 `/api/photo-meta/<编号>.json` 单独提供（只有
`id / ep / degraded / style / at`），取图页优先读它、读不到才退回 `/api/state`。

### 抠像：把人贴进官方主视觉的人像窗

主视觉的构图里**本来就留好了一块人像窗**：左上角是标题、右侧是芯片，左栏中下部
一整块连续暗场没有任何元素 —— 那块就是窗。「开发者证件照」要做的就是
**把人抠出来贴进那块窗**。这条链路有三道保险：

| 层 | 做法 | 代价 |
|---|---|---|
| 1 · 主路 | 有检测框 → **按人框裁切**跑 MODNet（逐像素软 alpha，发丝和半透明边都在） | CPU ~270 ms |
| 2 · 重试 | 裁切这一路没找到人 / 与检测掩码 **IoU < 0.30** → **整幅再跑一次**（人贴很近时整幅更好） | 再加 ~270 ms |
| 3 · 兜底 | 还不行 → 退用检测掩码的羽化版（边糊但有人）；连人都没有 → 不挂 alpha，整幅取景 | 0 ms |

**为什么「先裁切」——这是量出来的，不是猜的。** 把同一张人像按「占画面高
20% / 30% / 40% / 55% / 75% / 95%」合成到 2592×1944 展台画布上，与参考 alpha 比 IoU：

| 人占画面高 | 按人框裁切（外扩 1.25×） | 整幅直出 |
|---|---|---|
| 20% | **0.87** | 0.00 |
| 30% | **0.91** | 0.20 |
| 40% | **0.91** | 0.61 |
| 55% | **0.63** | 0.39 |
| 75% | **0.76** | 0.70 |
| 95% | 0.54 | 0.54 |

人越小差距越大，而展台本来就是「人站着、镜头包一大片背景」——整幅喂进去
等于把人缩没了。**所以主路是裁切，整幅是退路**（2026-09-14 更正：
早期版本反过来，依据是「同一张图只改裁切起点，覆盖率 0.268→0.020」这一次观测；
后来六档扫描发现那次是框本身没套住人，不是裁切的锅）。

**为什么是 MODNet，不是更大的模型**（本机同一张 500×375 人像，实测）：

| 模型 | 输入 | 耗时 | 覆盖率 |
|---|---|---|---|
| **MODNet** | 256² | **298 ms** | 0.268 |
| u2net_human_seg | 320² | 1203 ms | 0.274 |
| rmbg14 | 1024² | 3059 ms | 0.272 |

三者出图的边在同一观感档，贵的那两个没换来更好的边，只换来 4~10 倍等待。

**但"换模型"不是唯一的提精度手段 —— 同一个模型的输入分辨率也是。**
MODNet 的输入是**动态维度**，早期按 256² 写死是白丢精度。现场同一张 1920×1080 抓拍、
同一个扩充后的人像裁切（1579×1080），只改输入边长：

| 输入边长 | 真机耗时（CPU） | 说明 |
|---|---|---|
| 256² | 326 ms | 早期默认。alpha 要放大 6 倍才到裁切尺寸，边是糊的 |
| 384² | 764 ms | |
| **512²** | **1340 ms** | 现在默认。放大 3 倍 + 边缘细化，观感差一个档 |
| 640² | 2088 ms | 边际收益已经很小 |

多花的这 1 秒，端到端预算（≤35 s/人、中位 ~3.5 s）里放得下。

**三条纪律（都是踩出来的，见 `knowledge/04` 坑 7–9）**：

- **不要拿检测掩码当抠像。** YOLOE 给的是「框 + 框内多边形」，边是折线、发丝全丢 ——
  成片里的人像会像从一块方框里挖出来的。检测框**只用来看「看哪儿」**，不作为最终的边。
- **别用一次观测推翻流程。** 「整幅直出更稳」这条曾经写进纪律，实际是拿一个
  没套住人的框量出来的。凡是要定阈值/顺序的决定，**按人占画面的比例扫一遍再定**。
- **抠像模型不能上 AI 核。** MODNet 的 BatchNormalization 让 SpaceMIT EP
  **编译失败并硬崩**（`operator compile failed at node (BatchNormalization_197)`），
  整个 worker 进程直接死 —— 这不是「慢一点」，是 `std::terminate`，
  `try/except` 拦不住。所以 `_session(..., cpu_only=True)` 钉死在 CPU。

**「非空 ≠ 对了」**：覆盖率阈值只能拦住全空，拦不住自信的错答案，
所以才要那道 IoU 一致性闸门。这跟 `knowledge/04` §二「验收指标骗人」是同一个病。

### 成片里只有人：窗内不叠任何东西

现场判定成片人像窗里的姓名牌（姓名 / 编号 / 风格 / RISC-V 助记符 / `#SpacemiTDevCon`）
和右上角的算力徽章是**多余的「加框加字」**，已全部去掉。现在成片就是官方主视觉这一张，
人贴在预留窗口里，别的什么都不加。`keyvisual.compose()` 仍**保留**那批参数
（名称、编号、算力……）以便调用方不改，但不再参与构图。

配套的三件事，都是为了让「贴上去的边」干净 —— 它们跟模型准不准是两回事：

| 做法 | 治什么 |
|---|---|
| 抠像层的**掩码外填原片**，不填暗底 | 软 alpha 的过渡带会按比例混进垫在下面的像素；垫暗底就混出一圈灰黑描边，人脸像蒙了层灰纱 |
| **去背景色污染**（`_decontaminate`） | 过渡带里原片像素本身就是「人+旧背景」的混合色；背景是亮窗时人周围会留一圈浅雾边 |
| alpha **不降采样回传**（`BOOTH_MATTE_MAX_SIDE=0`） | 640 的 alpha 放到 1000 的成片上再贴，等于把边放大 3 倍 |

**风格只剩「原色」一档**（现场定的，见 §三 `BOOTH_STYLE`）：证件照就该是本人的颜色。
高对比 / 单色 / 线框 / 网点那四档看着像海报、本人不认，代码已删（旧版资产清单已并入 `docs/`）。
`rim=None` 于是恒定生效 —— **不描边、不泛光**，成片就是「把人抠出来贴上去」。

**窗里为什么没有“多出来的矩形”。** 早期素材那块人像窗里画着一个**浅灰人形占位**
（原始素材就这样），不盖掉人的四周会露一圈浅灰，所以要往窗里糊一层暗底。

**“要不要盖”现在由注册表说了算，不再靠猜。** 这里原本是一段纯启发式 ——
「窗内中性灰且亮的像素就盖」。换上**亮调**那套底图之后它立刻误伤：亮底整块都
「中性灰且亮」，于是往窗里糊了一块深色矩形。**在暗底上一点都看不出来，在亮底上
就是一块明晃晃的黑方块**（同一个坑的第二张脸，见 `knowledge/04` 坑 20）。

现在每套底图在 `KEYVISUALS` 里声明 `placeholder`（有没有画占位）；声明没有就
直接返回 `None`，启发式只在声明「有」时用来定位占位在哪。当前两套都是 `False`，
所以一个像素都不盖 —— 这条分支留着待命，换成带占位的老素材时才会自己生效。

盖底本身也只剩一道极轻的上下渐变 —— 起先那块是「径向光 + 网格」，看着像往窗里贴了
一张卡片，**纹理会让“盖住的区域”变成“看得见的一个矩形”**。

**「框里其实没人」也是一种失败，而且最危险。** 检测报「1 人」、alpha 也有内容
（覆盖率 0.039），但那条 alpha 是贴着画面下沿的一块碎块 —— 镜头前只有桌面时就是这样；
取景框按包围盒中心取，框里 alpha 全 0 → 抠像交出一张空 alpha → 一个像素没贴上 →
**成片里只有底板，而接口全绿、`degraded=false`**。现在 `render_cutout()` 末尾有一道
闸门：alpha 覆盖率低于 `stylize.CUTOUT_MIN_COVER`（`0.02`）就返回 `None`，退回
「整幅兜底」（与「一个人都没检出」同一条退路），并在 render 步骤留痕
（操作员面板上看得到「 · 整幅兜底」）。阈值实测：真人是 0.30~0.49，误检碎块 0.0000。

**取景框的比例是硬约束**（`stylize._frame_box`）：以人像包围盒为中心扩 34% 的 pad，
再按目标画布的宽高比建框，最后夹进画面时**等比缩**。夹取那一步曾经写成宽、高各自
`min()`，于是「人满画面」时比例被改，人被横向压到 53% —— 现场的表现就是
「我的人像被压窄了？？」。自检项：`stylize.self_test()["frame_aspect_ok"]`。

### 入景暗调：把人往底板的光里拉一把

「现场拍的人」和「底板上的暗场」是两种光：补光打在脸上是亮的，底板是低照度、冷调。
直接贴上去的人像一张贴纸浮在画上。修法**不是把底板调亮**，而是给贴上去的人
过一道极轻的暗调 —— 底板一个像素不动（`render/keyvisual.py` 的 `_into_scene()`）：

| # | 环境变量 | 默认 | 做什么 |
|---|---|---|---|
| 1 | `BOOTH_PERSON_EXPOSURE` | `0.88` | 压曝光（压掉 12%） |
| 2 | `BOOTH_PERSON_SATURATION` | `0.94` | 微去饱和（底板本身低饱和） |
| 3 | `BOOTH_PERSON_AMBIENT` | `0.05` | 掺 5% 底板的冷色 `(18,33,58)` |

`BOOTH_PERSON_TONE=0` 整条关掉。抠像失败时「整幅当脸糊上去」的那条兜底路
（`_compose_wide`）**过同一道** —— 光的逻辑只有一套，不然同一晚的成片会出现
两种光。

**「稍微」是量出来的，不是目测的。** 拿真机实拍 `SM-2026-0065` 的抓拍 + 真机
alpha，本地重放定稿合成路径，四档对照（「窗内人均值」= 窗口里真人那部分的平均亮度）：

| 档 | 参数（曝光/饱和/环境） | 成片整体均值 | 窗内人均值 | 裁定 |
|---|---|---|---|---|
| 改前 | 不加 | 34.6 | 124.3 | 太亮，像贴纸 |
| A 轻 | 0.92 / 0.96 / 0.03 | 33.8 | 111.4 | 偏轻 |
| **B 中（采用）** | **0.88 / 0.94 / 0.05** | **33.5** | **104.9** | 现场要的「稍微」 |
| C 重 | 0.84 / 0.92 / 0.07 | 33.1 | 98.7 | 开始发闷 |

再用换底图后的真机实拍 `SM-2026-0071` 复核一遍：窗内人均值 111.2 → 94.0（−15%），
成片整体均值 32.3 → 31.5，**底板未动**。本地重放与 K3 出图逐像素比，平均差 1.26
（纯 JPEG 噪声）—— 确认线上跑的就是这套参数。

偏重就回调 `BOOTH_PERSON_EXPOSURE=0.90`（或 `0.92`）。自检项：
`keyvisual.self_test()["tone_ok"]`（压暗幅度落在 0.80~0.98）与
`tone_base_untouched`（窗口外必须一个像素都不变，实测 `tone_outside_max = 0.0`）。
对照图（内部样张，未随仓库发布）：整幅与窗内 2× 两版。

### 底图素材：两套，共用同一个窗，默认随机用

`app/assets/bg/` 现在有 **两张**（同一版主视觉的暗调 / 亮调两种打光）：

| 注册名 | 文件 | 标签 | 光 | 贴上去的人 |
|---|---|---|---|---|
| `dark`（默认） | `devcon2026-keyvisual-a.png` | 暗调芯片 | 低照度冷调棚拍 | 过一道「入景暗调」（压 12%） |
| `light` | `devcon2026-keyvisual-b.png` | 亮调芯片 | 白台面平打光 | **一点都不动** |

两套的**版面是同一个**（左上标题 / 左下留白 / 右侧芯片），所以人像窗共用一组坐标
`box = (0.0150, 0.4000, 0.271670, 0.9850)` → **411×526px**；
扫描实测「窗内有没有内容」的像素数 **0**（两张都是），边缘 0.897 / 1.199。
标题最低一笔在暗调那张是 y=354，窗口顶 y=360，**间隙 6px**。

**人贴上去的调子必须跟着底图走，不能一套参数打天下**（`_tone_spec()`）：
暗调那套把人的曝光压下去是「入景」；**同一个动作套到亮底上，人就比整个画面暗一档**，
换了个方向的突兀。所以每套底图在注册表里声明自己的 `tone`，`none` 的那套原样返回。
自检项：`tone_quiet_untouched`（声明「不压暗」的底图，人像必须**逐像素**不变）。

**没点名时随机挑一套**（`BOOTH_KV_RANDOM=1`，`keyvisual.pick()`）：同一晚的成片
一半暗调一半亮调。拍摄位那一排「背景」里第一档就是**随机**，按了具体某一套之后
还能再切回随机；点名了的具体某一套永远不会被随机顶掉。
设 `BOOTH_KV_RANDOM=0` 就固定用默认那套（要同一晚色调一致时用这个）。

**出图比例和成片对不上，不能随便裁。** 这两张源图都是
1536×864（**正好 16:9**），等比放到 1600×900 就行，一刀不用裁；
更早的素材是 1264×848（**1.49:1**），就必须裁。而构图把可用空间从三面锁死了：

| 区域 | 内容 | 能不能裁 |
|---|---|---|
| 左上（y < 0.40） | SpacemiT / DevCon 2026 标题字 | ❌ 字会被切 |
| 右侧（x > 0.29） | 芯片主体 | ❌ 主体会被切 |
| **底部** | 连续暗场 / 亮台面 | ✅ 唯一的余量 |

所以规则统一成「**按宽度铺满 → 顶部对齐 → 从下往上裁**」，
由 `tools/make_keyvisual.py` 的 `bake()` 离线烤成 **1600×900** 再进仓库。
好处是**运行期不再需要对齐参数** —— `box` 的归一化坐标
可以直接按 1600×900 量，而不是按原始出图量。

**人像窗是扫出来的，不是目测的。** `scan()` 在左栏里搜「边缘能量 + 亮度标准差」
最低、面积又不至于太小的 0.78 框。这次两张都收敛到同一个框（版面相同是好事）——
量完还要自己复核一遍「**窗内到底有没有内容**」：用大半径模糊当背景、找窗内的
显著像素，两张都是 0。

宽高比 **必须** 等于 `PORTRAIT_SIZE` 的 0.78：`_compose_cutout()`
是把抠好的人直接 `resize` 到窗口尺寸的，窗口比例差一点，
人就被横向或纵向拉变形（坑 19）。

改底图之后必跑一次自检（`python3 render/keyvisual.py`）：
`window_in_canvas` / `feather_ok` / `tone_ok` / `tone_base_untouched` /
`tone_quiet_untouched` 都得是 `true`；
`tools/preflight.py` 也会算 `assets/bg/*.png` 的个数（当前期望 **2**）。
