# 现场故障处置手册 · 装置 5「赛博开发者证件照」

面向**现场值守的非技术同事**。慌乱时照这一页做就行：先看症状，再做三步内的动作，再找人。
每条命令后面都标了是 【安全】 还是 【影响现场】。

> 【安全】= 只看状态、不会打断拍摄，随便跑。
> 【影响现场】= 会中断出图 / 会删东西 / 会重启服务，**做之前先跟旁边同事说一声**，并让正在拍的参会者稍等。

## 0. 先记住三件事

**① 三个页面就是三张牌**

| 打不开的时候 | 打开这个 | 看什么 |
|---|---|---|
| 不知道哪儿坏了 | `http://127.0.0.1:8090/operator`（操作员面板） | 相机 / 推理 worker / 存储与编号 / 一键处置 |
| 大屏没动静 | `http://127.0.0.1:8090/stage` | 实时预览、掩码、本次耗时、EP / CPU 徽章 |
| 参会者说取不了图 | `http://<局域网IP>:8090/p/<取图令牌>` | 大图、保存、删除入口（编号只是显示用）|

**② 一条命令看全部状态**（在 K3 的终端里跑；只想看清楚一点就加上后面的美化行）

```bash
curl -s http://127.0.0.1:8090/api/state
curl -s http://127.0.0.1:8090/api/state | /usr/bin/python3 -m json.tool | head -60
```

**③ 拿不准时，第一步永远是「一键恢复到就绪」**

- 在操作员面板上按钮点一下，或者：
```bash
curl -s -X POST http://127.0.0.1:8090/api/operator/restore
```
- 它做四件事：清空同意令牌、重开相机、复活推理 worker（含清残留的 AI 核占用）、清掉上一次的画面叠加层。
- **不影响已经出好的照片。** 【影响现场】会清掉当前这位参会者已经勾过的同意，**要请他重新勾一次**。

### 读状态的最小读法

| 字段（`/api/state` 里） | 正常 | 不正常时看这一节 |
|---|---|---|
| `camera.ok` | `true` | 相机不可用 → **A** |
| `camera.fourcc` | `MJPG` | 不是 MJPG，高分辨率下会慢到 1 fps → **A** |
| `camera.real` | `true` | `false` 表示在用 MOCK 合成源（不是真相机）→ **A** |
| `infer.ep` | `true` | `false` 表示没拿到 AI 核，在 CPU 上跑 → **B / C** |
| `infer.ep_fallback` | `null` | 有文字就是「为什么没拿到核」的原因 → **B** |
| `infer.preloaded` | `true` | `false` = 还在预热，第一个参会者要多等一会儿 |
| `counters.warmup_ms` | 一个数字 | `null` = 预热还没跑完 → **G** |
| `avg_infer_ms` | 约 200 | 约 1100 就是在 CPU 上 → **C** |
| `disk.free_gb` | 大于 5 | 掉到个位数 → **E** |
| `link_base` | `http://10.x.x.x:8090` | 是 `127.0.0.1` 手机就连不上 → **D** |

### 日志在哪

取决于服务是怎么起的：

```bash
# 按本手册/README 的 nohup 方式起的：看那个日志文件
tail -n 100 -f /opt/devcon/app/booth.log

# 如果部署时用了 systemd 单元（T-10 的 devcon-booth.service）
journalctl -u devcon-booth -n 200 -f
```

> 怎么知道这台机器是用哪种方式起的？跑一次：
> ```bash
> systemctl status devcon-booth
> ```
> - 有输出 → systemd 管着（日志走 `journalctl -u devcon-booth`，**断电后会自己起来**）；
> - 提示 `Unit devcon-booth.service could not be found` → 是手工 / `nohup` 起的（日志看 `booth.log`，**断电后要手工起**）。
>
> 装机命令（单元文件 `app/deploy/devcon-booth.service` 已入库，2026-09-14）：
> ```bash
> sudo install -m 0644 /opt/devcon/app/deploy/devcon-booth.service /etc/systemd/system/
> sudo systemctl daemon-reload && sudo systemctl enable --now devcon-booth
> ```
> 这份单元在真机上装没装、断电能不能自启，**还没有实测记录**（见 `app/README.md` 第六节 V9）。

## A. 相机不出图 / 黑屏 / 掉线

**症状**：拍摄位或大屏的预览是黑的 / 卡住不动；抓帧报错「相机重连中」；面板「相机」一栏是红的。

### 三步

**第 1 步【安全】确认系统还认不认这台相机**

```bash
v4l2-ctl --list-devices
ls -l /dev/v4l/by-id/
```

- 期望看到 **DICOTA 4K**，采集节点是 **`/dev/video1`**。
- `/dev/video0` 是 Linlon 硬件编解码（**不是相机**），`/dev/video2` 是 metadata 节点（抓不到帧）。
- 期望 by-id 路径存在：
  `/dev/v4l/by-id/usb-DHZJ-240124-ZJ_DICOTA_4K_01.00.00-video-index0`
- **完全看不到 DICOTA** → 是线 / 口 / 供电问题：换一个 USB 口，换一根线（**优先用板子上的 USB3 口，别用劣质扩展坞**）。

**第 2 步【安全】看服务这边的读数**

```bash
curl -s http://127.0.0.1:8090/api/state
```

看三处：`camera.ok`、`camera.fourcc`、`camera.detail`。

- `camera.ok=false` → 相机没打开成功。
- `camera.fourcc` **不是 `MJPG`** → 协商失败掉到了 YUYV，高分辨率下只有 1 fps（等于不可用）。**重新插拔 USB** 再让它自己重开。
- 就相信面板上的「数据源」：写着 **MOCK 合成源** 就是没在用真相机。
- 画面有**横向滚动的条纹 / 一条条亮暗带** → 这是**灯光频闪**（中国市电 50 Hz），不是相机坏了。
  代码起服务时会用 `v4l2-ctl` 把它设成 50 Hz（`camera.set_powerline_50hz`），
  开场预检里能看到 `power_line_frequency=50Hz` 这一条。如果**设了还照样有条纹**，
  那就是灯本身在闪，软件救不了。
  现场动作：先把相机的补光灯调成直流 / 关掉，或换个拍照角度；录像留证并找装置 5 软件负责人。

**第 3 步【影响现场】一键恢复，还不行就指定设备重开**

```bash
# 先试一键恢复（重开相机 + 复活推理）
curl -s -X POST http://127.0.0.1:8090/api/operator/restore

# 还不行：指定设备路径重开（先停掉正在跑的服务，再起）
pkill -f booth_server.py
BOOTH_CAMERA_DEVICE=/dev/v4l/by-id/usb-DHZJ-240124-ZJ_DICOTA_4K_01.00.00-video-index0   nohup /usr/bin/python3 /opt/devcon/app/booth_server.py >> /opt/devcon/app/booth.log 2>&1 &
```

> **指定了 `BOOTH_CAMERA_DEVICE` 就等于是立了规矩**：装置只会用这个节点；它不在，
> 就**明确报错**「指定的设备不存在」，**不会**偷偷换成另一台相机。
> 看到这条错误时，去 `camera.health` 里的 `resolved` 字段看**当前实际存在**的节点，
> 再把环境变量改成它 —— 不要以为它自己会兜住。
> 另外，按上面的方式手工起服务时记得**先停掉 systemd 那个**（`systemctl stop devcon-booth`），
> 否则 8090 端口被占，新进程起不来。

### 相机整个从系统里消失了：USB 总线复位【影响现场】

**怎么认出来**：操作员面板「设备」一行写着「未解析」，或者预检里出现

```
[FAIL] by-id 解析  · 既没有 DICOTA 的 by-id 链接，也没有 /dev/video1
```

再看一眼内核日志。有下面这一段，就是相机从总线上掉下去了：

```
uvcvideo 7-1.1:1.1: Failed to set UVC probe control : -71
usb 7-1.1: USB disconnect, device number 71
usb 7-1-port1: Cannot enable. Maybe the USB cable is bad?      ← 连报好几次
usb 7-1-port1: unable to enumerate USB device
```

**为什么「一键恢复」救不回来**：那一步做的是「关掉句柄、重新打开设备节点」。
相机掉线之后 `/dev/v4l/by-id` 整个目录都没了，节点压根不存在，重开无从谈起。
这时候只有让内核把这条 USB 控制器重新枚举一遍，那个口才会重新上电。

**动作**：操作员面板 → 「USB 总线复位（相机掉线自救）」，约 10~20 秒。

```bash
# 等价命令
curl -s -X POST http://127.0.0.1:8090/api/operator/usb-reset
```

- 这条总线上的**其它 USB 设备也会跟着重连一下**（本机这条总线上只有相机和一个
  USB 扩展坞），所以它会打断别的 USB 设备几秒。这是代价，不是故障。
- 复位后设备号通常会变（现场实测 video2 → video1）—— 这是正常的，程序按 by-id 找，
  不用改任何配置。
- 返回里 `after.ok` 为 `true` 才算救回来了。是 `false` 就别再点了，动手查线：
  **换一根 USB 线、换一个口，尽量直插 K3 不要走 hub**（相机掉线多半是供电/线材）。
- 相机彻底掉线时程序自己也会试一次复位（不会反复试，有 30 秒冷却），
  成功与否都记在 `preview.camera.last_usb_reset_note` 里。

**总线被内核整个注销的情况（2026-09-15 实测）**：还有一种更狠的掉线，
dmesg 里是这一段：

```
usb usb7: USB disconnect, device number 1
onboard-usb-dev 7-1: USB disconnect, device number 2
usb 7-1-port1: attempt power cycle
xhci-hcd xhci-hcd.15.auto: USB bus 7 deregistered          ← 整条总线注销
```

这时控制器（如 `xhci-hcd.15.auto`）**还在 sysfs 里**，但驱动已经被内核解绑了。
旧版本的复位会无条件先 `unbind`，于是直接报

```
unbind xhci-hcd.15.auto 失败：OSError: [Errno 19] No such device
```

—— 明明 `bind` 一下就能好。现在程序会先判断该走哪条路
（`camera.usb_reset_plan`）：驱动还绑着就 unbind+bind，已被解绑就**直接 bind**。
正常情况下点「USB 总线复位」就能救回来，结果里会写 `plan`。

万一还是不行（`after.ok=false`），SSH 上机手工绑一次：

```bash
# 1) 控制器还在不在（在 = 还有救）
ls -d /sys/devices/platform/soc/*/xhci-hcd.*
# 2) 驱动绑没绑（列表里没有它 = 就是上面那种情况）
ls /sys/bus/platform/drivers/xhci-hcd/
# 3) 直接绑回来（把 xhci-hcd.15.auto 换成实际那个）
echo xhci-hcd.15.auto > /sys/bus/platform/drivers/xhci-hcd/bind
# 4) 等 5~10 秒，by-id 会自己回来
ls -la /dev/v4l/by-id/
```

第 1 步就什么都找不到的话，软件这边就没有办法了 ——
换线、换口，或者重启一次 K3。

**该找谁**：换线 / 换口 / 换供电 → 现场搭建物资负责人。

### 相机反复掉线，但换不了硬件：把拍照分辨率降到预览档

如果现场已经没法换线换口，而相机还是在连拍中途掉总线上，可以退一步：
**让拍照分辨率和预览分辨率一样**，这样一次拍摄里就没有任何分辨率切换。

```bash
# 先停服务，再用环境变量起（或者在 /etc/devcon/booth.env 里加这一行）
BOOTH_PHOTO_SIZE=1280x720
```

代价是成片人像的来源从 1920x1080 降到 1280x720。要不要接受这个代价，看现场：

| 拍照分辨率 | 每次拍摄的分辨率切换 | 中位耗时 | 折算吞吐 |
|---|---|---|---|
| 1920x1080（默认） | 2 次 | 4.31 s | 836 人/小时 |
| 1280x720 | 0 次 | **2.92 s** | **1232 人/小时** |

（成片的人像窗只有约 278x357 px，所以 1920 那档多出来的像素并不会让成片更清晰。）


### 相机彻底坏了：开 MOCK 兜底【影响现场】

MOCK 用**程序画出来的人形**当画面，不拍真人。AI 推理、风格化、编号、二维码、取图链路照常跑，
适合「相机坏了但演示不能停」的时候。界面上会亮一个 **「MOCK 合成源」** 徽章，`camera.real` 会是 `false`。

```bash
pkill -f booth_server.py                      # 先停掉正在跑的（否则 8090 端口被占，起不来）
# 方式一：命令行开关
nohup /usr/bin/python3 /opt/devcon/app/booth_server.py --mock-camera   >> /opt/devcon/app/booth.log 2>&1 &
# 方式二：环境变量（等价）
BOOTH_CAMERA=mock nohup /usr/bin/python3 /opt/devcon/app/booth_server.py   >> /opt/devcon/app/booth.log 2>&1 &
# 起完确认
curl -s http://127.0.0.1:8090/api/state
```

- MOCK 下**没有真照片**：出的是合成人形。别当成真实拍摄对外宣传。
- 恢复真相机：按上面不带 `--mock-camera` 的命令重新起一次。

**该找谁**：换线 / 换口 / 换相机 → 现场搭建物资负责人；确认是软件侧打不开 → 装置 5 软件负责人。

## B. 大屏不动 / 掩码不成形 / 徽章显示 CPU

### B-1 大屏完全不动

**三步**

```bash
# 1)【安全】大屏浏览器还在不在
pgrep -af chromium

# 2)【安全】服务还在不在
curl -s http://127.0.0.1:8090/api/health

# 3) 页面本身卡住了就重开 kiosk【影响现场】（大屏会黑一下）
pkill -f 'chromium.*--kiosk'
chromium --kiosk --app=http://127.0.0.1:8090/stage &
```

> 大屏页面**不会主动弹错误提示**，这是刻意的（现场不吓人）。所以「不动」时要靠上面两条命令判断，
> 不要盯着画面猜。大屏是只读的，重开它不会影响出图。

### B-2 掩码不成形（人像轮廓没出来）

```bash
curl -s http://127.0.0.1:8090/api/overlay.json
```

看 `person_count`、`mask_applied`、`degraded`、`degraded_reason`：

| 看到什么 | 含义 | 动作 |
|---|---|---|
| `person_count: 0` | 这一张没检到人 | 请参会者站进取景框、肩线对齐上三分线、光别背对 → **重拍一张** |
| `mask_applied: false` 且 `degraded: true` | 这次没抠像（走了 L0） | 成片照常给，见 **I** |
| `mask_applied: true` | 正常 | 掩码只是画得淡，不是没成形 |

### B-3 ★ 徽章显示 CPU，而不是 EP SpaceMIT

**这不是界面 bug，是如实上报。** 意思是：**AI 核被别的进程抢走了，推理现在跑在 CPU 上。**
界面上的 `CPU` 字样是系统故意写上去的 —— 诚实字段，**不许为了好看改成 EP**。

```bash
# 1)【安全】确认是「没拿到核」，以及原因
curl -s http://127.0.0.1:8090/api/state
#    看 infer.ep（应为 false）、infer.ep_fallback（原因文字）、infer.ep_threads

# 2)【安全】谁抢了核：先看 8080 那个常驻演示（yolos-box 占着 8080）
ss -ltnp | grep -E ':8080'
pgrep -af 'yolos|yoloe'
#    也检查是不是我们自己多起了一份服务（两份服务会互相抢核）
pgrep -af booth_server.py
```

**三步处置（从轻到重）**

1. 【影响现场】点操作员面板的「一键恢复到就绪」（或 `curl -s -X POST http://127.0.0.1:8090/api/operator/restore`）——
   它会重启 worker，并在拿不到核时先清掉残留的 TCM 占用再重试一次。
2. 【影响现场】如果确认 8080 的演示没人在用，把它停掉，再回到第 1 步：
```bash
systemctl stop yolos-box      # 若该服务存在；会停掉 8080 端口那个演示
```
3. 【安全】实在拿不到核就先继续出图：徽章显示 CPU、每帧约 1.1 秒（比 AI 核慢约 5.7 倍，见 **C**），
   **成片照常给**。等空档再回来处理。

**该找谁**：装置 5 软件负责人（涉及 8080 那个演示要不要停，需要现场决策）。

## C. 出图变慢

**先记住两个量级**（来自真机实测，`系统规格 v2（内部文档） §1.2`）：

| 情况 | 每帧推理 | 感受 |
|---|---|---|
| 拿到 AI 核（EP SpaceMIT） | **约 0.2 秒**（205 ms） | 正常 |
| 退到 CPU 兜底 | **约 1.1 秒**（1160 ms） | 慢约 5.7 倍，出图前明显多等 |

### 三步

**第 1 步【安全】判断是「CPU 兜底」还是「别的原因」**

```bash
curl -s http://127.0.0.1:8090/api/state
```

- `infer.ep=false` + `counters.cpu_infers` 在涨 → **CPU 兜底**，按 **B-3** 处理（被别人抢核）。
- `infer.ep=true` 但 `avg_infer_ms` 还是很大 → 不是核的问题，往下看。
- `counters.warmup_ms` 为 `null` → **模型还在预热**，第一个参会者本来就要多等（首帧约 1.2 秒）。
- `disk.free_gb` 很小 → 磁盘问题，见 **E**。

**第 2 步【安全】看最近一次的分解耗时**

```bash
curl -s http://127.0.0.1:8090/api/overlay.json
```

看 `infer_ms`（推理）和 `/api/state` 的 `avg_infer_ms`（近 20 次均值）。

**第 3 步**

- 是 CPU 兜底 → 按 **B-3** 的三步走。
- 是磁盘快满 → 按 **E** 腾空间。
- 都不是，但中位耗时明显超过 35 秒/人 → 【影响现场】一键恢复一次；仍不行就换备用机（见 **G** 结尾）。

**该找谁**：装置 5 软件负责人。

## D. 二维码扫不出来 / 手机打不开取图页

**取图链接长这样**：`http://<K3 的局域网 IP>:8090/p/<取图令牌>`

令牌是 **22 位随机串**（形如 `V3f2O3CT2bl_Yt8hov2LLQ`），**不是编号**。
编号 `SM-2026-0007` 那种是**连号**的，只显示在面板和取图页上，
**拿编号拼链接一定打不开**（那条路是故意堵死的：编号可枚举，
当入口等于把全场照片挂到公网上）。

二维码里编码的就是这个令牌地址（生成时取当时的地址，见下面「缓存」那条）。

### 三步

**第 1 步【安全】看现在的取图地址是什么**

```bash
curl -s http://127.0.0.1:8090/api/state
#    看 link_base；操作员面板最底下那行也会显示「局域网地址 …」
```

**第 2 步【安全】按可能性逐个排除**

| 现象 | 原因 | 动作 |
|---|---|---|
| `link_base` 是 `http://127.0.0.1:8090` | K3 没拿到局域网地址（没插网线 / 没连热点） | 接上网线或开热点，让 `link_base` 变成 `10.x` / `192.168.x` |
| 手机打不开任何页面 | 手机和 K3 **不在同一个网络** | 让手机连到同一个 Wi-Fi / 热点 |
| 手机能开别的网站，就是开不了 8090 | 服务只监听了本机 | 跑 `ss -ltnp`，在输出里找 8090 那一行：期望是 `0.0.0.0:8090`；若是 `127.0.0.1:8090`，说明启动时 `BOOTH_HOST` 被限成了本机 → 【影响现场】重启服务时去掉该限制 |
| 手机打不开、但服务正常 | 可能有防火墙 / 网络隔离 | 用手机浏览器打开 `http://<link_base>/api/health`；能出 `{"ok":true,...}` 说明通，不出就是网络侧 → 找展位保障 |

**第 3 步** 现场最快的兜底：**让参会者手输链接**（把 `http://<K3 IP>:8090/p/<取图令牌>` 念给他）。
但令牌是 22 位随机串，念不清也抄不准 —— 更快的做法是**让他原地重拍一张**，
或者在操作员面板「最近成片」里点那张的「取图页」按钮，把地址栏给他看。
比修复网络快得多。

### 换了地址之后，旧二维码会指向旧地址（缓存）

二维码 PNG 是**第一次生成时**按当时的地址写死缓存的（`data/qr/<令牌>.png`）。
如果中途换了 IP / 域名，旧编号的二维码还是老地址：

```bash
# 【安全】删掉那张缓存，下次打开 /api/qr/<令牌>.png 会按新地址重新生成
rm -f /opt/devcon/app/data/qr/<令牌>.png
```

已经发出去的旧二维码没法追回 —— 所以**地址要在开场前定死，别中途改**。

### 扫码扫不出来（画质问题）

- 手机亮度调到最高；别用带滤镜 / 美颜的第三方扫一扫，用系统相机或微信扫。
- 屏幕反光、手指挡住、二维码太小 → 换个角度，或直接把链接念给参会者。

★ **二维码在 iOS / Android 真机上的扫码结果，截至本手册完稿尚未在真机验证过**
（只有独立解码器回环测试）。**彩排必须真机扫一次**，别等开场。

**该找谁**：网络 / 局域网 → 展位保障；服务地址配置（`link_base`、`BOOTH_PUBLIC_HOST`）→ 装置 5 软件负责人。

## E. 磁盘满

**症状**：出图失败、面板上出现错误；参会者拿到编号但取不到图。

### 三步

```bash
# 1)【安全】看余量（若改过 BOOTH_DATA，把路径换成实际的数据目录）
df -h /opt/devcon/app/data

# 2)【安全】看是谁占的
du -sh /opt/devcon/app/data/* | sort -h
```

**第 3 步：按「损失从小到大」腾空间**

```bash
# ①【安全】面板上的「按留存期清库」= 只清超过 7 天的（现场当天通常一张都不会被清掉）
curl -s -X POST http://127.0.0.1:8090/api/operator/purge

# ②【影响现场】先删「原片」—— 它只用于当时的推理，删掉不影响已出的成片与取图
rm -f /opt/devcon/app/data/captures/*.jpg

# ③【影响现场】还不够就按编号整张删（不可恢复，先核对编号）
curl -s -X DELETE http://127.0.0.1:8090/api/photo/SM-2026-0007
```

### 必须知道的诚实说明

- **代码里没有「内存队列」**：规格书 §9 写的「磁盘写失败 → 内存队列 + 操作员告警」在实现里不存在。
  真实行为是：**本次任务直接失败**，操作员面板的「降级与错误」里能看到原因。
- 写失败时编号可能已经发出去了，但照片文件不存在 → **腾出空间后，请这位参会者重拍一张**，
  并跟他说明「刚才那张没存下来，不好意思」。已删除 / 未落盘的编号不会再被复用，不用担心撞号。

**该找谁**：装置 5 软件负责人；需要拔盘 / 换盘 → 展位保障。

## F. 编号不对

编号规则：**`SM-<年份>-<4 位序号>`**（例 `SM-2026-0007`），由发号器落盘保存，重启不归零。

```bash
#【安全】看当前发号器
cat /opt/devcon/app/data/counter.json

#【安全】数一下今天实际出了多少张（对比发号器）
ls /opt/devcon/app/data/photos/*.jpg | wc -l
```

| 现象 | 原因 | 动作 |
|---|---|---|
| 从 `SM-2026-0000` / 0001 重新开始 | `counter.json` 里的年份不是当年（年份不一致会从 0 重来） | 确认系统日期年份正确 |
| 编号跳号 | 之前有任务失败但编号已经发出 | 属正常，不必处理 |
| 序号超过 9999 | 格式会自然变成 5 位（如 `SM-2026-10000`） | 正常，页面显示不受影响 |
| 面板「已出图」比实际文件多 | 面板显示的是**发号计数**（含已删除的） | 要数现存文件用上面第二条命令 |

**要手工改发号器**【影响现场】：

```bash
pkill -f booth_server.py                                        # 先停服务
# 编辑 counter.json，把 value 改成想要的数字（年份要保持当年）
/usr/bin/python3 - <<'EOF'
import json
p = "/opt/devcon/app/data/counter.json"
d = json.load(open(p, encoding="utf-8"))
d["value"] = 100          # 改成想要的起始值
json.dump(d, open(p, "w", encoding="utf-8"), ensure_ascii=False)
print(d)
EOF
nohup /usr/bin/python3 /opt/devcon/app/booth_server.py >> /opt/devcon/app/booth.log 2>&1 &
```

**服务运行中直接改 `counter.json` 是无效的**（内存里的计数下一次发号就会把文件覆盖回去），
所以必须「停服务 → 改 → 起服务」。

**该找谁**：装置 5 软件负责人。

## H. 参会者要删除照片 / 行使删除权

**合规要求：这是他本人的权利，必须当场完成，不要「待会儿弄」。**

取图页最底下有一个**「删除我的照片」**按钮 → 确认 → 页面显示「已删除」，**图片链接立即失效**。

## I. 降级徽章「L0」是什么意思

**L0 = 保底层：这次没有抠像，直接把整幅照片做风格化，水印、编号、二维码照常给 —— 成片照常交付。**

触发条件（任一）：

- 推理超时（超过 `BOOTH_INFER_TIMEOUT`，默认 **2.5 秒**）；
- 推理报错（worker 挂了 / 模型出错）；
- 合成失败时还会再退一步：**原片 + 水印 + 编号**（朴素但一定有图）。

怎么看：

```bash
curl -s http://127.0.0.1:8090/api/overlay.json
#   看 degraded（true/false）、degraded_reason（原因）、mask_applied
```

- 大屏和拍摄位会显示「**L0 降级**（成片照常生成）」加一行原因；
- **参会者照样拿到照片**，这是硬规则：推理失败绝不让参会者空手离开。
- 对参会者可以这样说：「这张是整幅风格化版；AI 抠像这次没赶上，照片照常给你。」

**该找谁**：偶发一次不用找人；**连续多次 L0** → 装置 5 软件负责人（通常与 AI 核被抢有关，见 **B-3**）。

## M. 不要做的四件事

1. **不要 `kill -9` 推理进程或服务。** 强杀会泄漏 TCM block，之后 AI 核会一直显示被占、推理全部退化。
   要停就用普通结束信号（`pkill -f booth_server.py` 或 `systemctl stop`）。
   已经强杀过了 → 点「一键恢复到就绪」（worker 会被重启，重启后的首次加载会先尝试清理残留的 AI 核占用再拿核）。
2. **不要为了好看把徽章改成 EP SpaceMIT。** 显示 CPU 就是真的在 CPU 上跑，这是**如实上报**，
   也是这个装置的卖点之一（真实读数、真实加速、真实降级）。
3. **不要用 venv 的 python 起服务。** 必须是 `/usr/bin/python3`（riscv64 上 venv 里没有 onnxruntime 轮子）。
4. **不要在现场同时起两份服务、也不要在观众面前跑压测脚本。** 两份服务会互相抢 AI 核，
   大屏徽章会变成 CPU、出图变慢（约 1.1 秒/帧）。
