# 装置 5 · 软件部署与故障处置

> **先读这三行，能省一次现场返工：**
> **现场系统在 `app/`。** 仓库只包含 `app/` 这一份现场实现；更早的浅色版原型
> （浏览器拍照、`/booth` 路由）未随开源发布，不要照它部署。
> 真正要照做的两份文件是：`app/deploy/README.md`（部署 / 预检 / 大屏 kiosk）
> 与 `app/docs/现场故障处置.md`（面向非技术同事的排障手册）。
> 本页只回答三件事：**它长什么样、怎么起、现在是什么状态。**

真机：`root@192.0.2.10`（K3 Pico-ITX，Bianbu 4.0.1，8 核 / 7.7 GiB）
代码：`/opt/devcon/app`　数据：`/opt/devcon/app/data`　模型：`/opt/devcon/assets/models`
端口：**8090**　解释器：`/usr/bin/python3`（**禁止 venv、禁止 pip**）

## 1. 系统构成（`app/`）

```
app/
├── booth_server.py    控制面（纯标准库 HTTP，端口 8090）—— 唯一入口
├── camera.py          UVC 抓帧（全项目唯一 import cv2 的地方）
├── infer_client.py    推理客户端（worker 子进程 / 无 worker 时走 L0）
├── store.py           编号发号器 + 记录落盘 + 留存删除
├── infer/
│   ├── worker.py      推理 worker（唯一 import onnxruntime/spacemit_ort 的地方）
│   └── tokenizer.py   文本编码（BPE）
├── render/
│   ├── keyvisual.py   成片合成（官方主视觉底版，输出 1600x900）
│   ├── stylize.py     四种风格化
│   ├── card.py        早期卡片版面（保留，`BOOTH_CARD=keyvisual` 为默认）
│   ├── watermark.py   水印 / 编号 / 指令角标
│   └── qr.py          二维码编码（纯 Python，离线）
├── static/            四个界面（原生 HTML/JS，无框架无构建）
│   ├── index.html       拍摄位     /
│   ├── stage.html       大屏算力视图 /stage
│   ├── operator.html    操作员面板 /operator
│   └── pick.html        取图页     /p/<令牌>
├── deploy/            devcon-booth.service + 部署说明
├── docs/              现场故障处置手册 + 彩排记录
├── tests/             控制面契约 / 端到端 / 相机 / 二维码
└── tools/             preflight.py（开场前逐项预检）/ deploy.sh / 出样张
```

**依赖**：`Pillow`、`numpy`、`cv2`、`onnxruntime`、`spacemit_ort` —— Bianbu 上已预装。
不需要 pip、不需要 node、不需要构建。

**为什么拆成两个进程**：`cv2` 与 `spacemit_ort` 同进程会崩（见 `docs/spec/系统规格-v2.md` §1.1），
所以抓帧（`camera.py`）和推理（`infer/worker.py`）必须在不同进程，`booth_server.py` 只做编排。

## 2. 起服务与重启

```bash
# 手工起（排障用；日志在终端里）
cd /opt/devcon/app && /usr/bin/python3 booth_server.py --host 0.0.0.0 --port 8090

# 无相机时用合成源（界面会带 MOCK 黄标，不会假装是真相机）
/usr/bin/python3 booth_server.py --port 8090 --mock-camera
```

```bash
# 开机自启（现场推荐）
install -m 0644 /opt/devcon/app/deploy/devcon-booth.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now devcon-booth
systemctl status devcon-booth --no-pager
journalctl -u devcon-booth -n 60 --no-pager
```

> **重启服务**（改完代码最常用的一条）：
> `pkill -f "[b]ooth_server.py"` 再起。
> 方括号不能省 —— 不写的话 `pkill -f` 会匹配到你自己这条命令，把当前 shell 一起杀掉。
> 服务只起一个实例，**两个实例抢同一个相机 = 两个都不可用**。

## 4. 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 探活（进程在不在） |
| GET | `/api/state` | 相机 / 推理 / 计数 / 磁盘 / 最近成片 |
| GET | `/api/overlay.json` | 大屏用：最近一次的推理耗时、EP、端到端、人数 |
| GET | `/api/preview.mjpg` | 取景流（MJPEG，多客户端可同时拉） |
| GET | `/api/job/<id>` | 单个拍摄任务的分步进度 |
| GET | `/api/photo/<令牌>.jpg` · `/api/thumb/<令牌>.jpg` · `/api/mask/<id>.png` · `/api/qr/<令牌>.png` | 成片 / 缩略图 / 掩码 / 二维码（掩码是内部件，仍用编号）|
| POST | `/api/consent` | 领取同意令牌（`agree:false` 不发） |
| POST | `/api/capture` | **拍摄**（需 `X-Booth-Session`，无有效令牌一律 403） |
| POST | `/api/operator/restore` | 一键恢复到就绪 |
| POST | `/api/operator/purge` | 按留存期清库 |
| POST | `/api/operator/reset` | **彩排清场**（见 §6） |
| DELETE | `/api/photo/<令牌>` | 参会者自助删除（保留 tombstone 审计）；令牌就是凭证，编号删不掉 |

风格取值：`highcontrast` · `mono` · `dieline` · `halftone`（默认 `highcontrast`）。
运行期可调的环境变量：`BOOTH_DATA`、`BOOTH_CAMERA`、`BOOTH_CAMERA_DEVICE`、
`BOOTH_PREVIEW_FPS`、`BOOTH_RETENTION_HOURS`、`BOOTH_CONSENT_TTL`、`BOOTH_CARD`、
`BOOTH_SEG_MODEL` / `BOOTH_DET_MODEL` / `BOOTH_CLIP_MODEL`、`BOOTH_EP_THREADS*`、
`BOOTH_PUBLIC_HOST`、`BOOTH_ACCESS_LOG`。

## 6. 彩排清场（活动开始前必须做一次）

彩排会拍掉几百张，编号和 `已出图` 会被推高。清场把它们清掉，**让大屏上的数字是活动的真实成绩**。

操作员面板 →「**彩排清场（清空成片与编号）**」，或：

```bash
curl -s -X POST http://127.0.0.1:8090/api/operator/reset
```

它会：删掉全部成片/缩略图/原片/掩码/二维码 → 编号归零 → 记录归档为
`records.jsonl.bak-<时间戳>` → 作废所有同意令牌 → 清零降级/错误计数。
**和「按留存期清库」不是一回事**：那个按 7 天删，当天拍的删不掉。

> 测试套件已经不会污染现场数据了：`tests/test_server.py` 用 `/tmp/booth-test-data`，
> `tests/e2e_test.py` 用 `/tmp/booth-e2e-data-<端口>`。跑测试不影响 `data/`。

## 7. 常见故障（详细版见 `app/docs/现场故障处置.md`）

| 症状 | 先做这个 |
|---|---|
| 大屏四个指标一直「—」 | 正常：还没人拍。拍一张就会跳出真实读数 |
| 取景框一直是黑的 / 不动 | 页面每 4 秒自检一次、最长约 12 秒会自动重连，并在画面上显示「相机重连中…」。仍黑着就看 `/api/state` 的 `preview`：`seq` 不涨=服务端没出帧、`camera.reopens` 在涨=相机掉线过、`last_error` 写着原因 |
| 预览老是断流（画面停住/黑屏） | 先看 `dmesg -T \| grep -E "uvc\|usb 7"`：出现 `error -71`、`probe with driver uvcvideo failed`、`USB disconnect` 就是**链路的物理问题**（相机 USB 口/线缆/供电），不是软件。软件侧已做三层：相机句柄废掉后自动重开（6s 冷却）、前端画面冻结自动重拉、systemd 看门狗在进程真卡死时重启服务。根治要换 USB 口（直插板子、别挂 hub）、换短线 |
| 拍摄失败：打不开相机 | 看有没有第二个进程占着相机：`pgrep -af "[b]ooth_server.py"`、`pgrep -af "[c]amd.py"`，多出来的杀掉，再 `POST /api/operator/restore` |
| 界面带 MOCK 黄标 | 相机没起来，正在用合成源。**成片不能发给参会者** |
| EP 徽章变 CPU | 没拿到 AI 核。`POST /api/operator/restore`；仍不行看操作员面板的「降级原因」 |
| 手机扫不出二维码 | 确认 `link_base` 是 `http://192.0.2.10:8090` 而不是 `127.0.0.1` |
| 成片里人像是灰块 / 只有轮廓 / 人没抠进来 | 抠像没成。看 `/tmp/booth.log` 里的 `抠像不可用` 与响应里的 `matte_source`：`modnet-roi`=按人裁切成的（正常主路）、`modnet`=退到整幅成的、`detect-mask`=退到检测掩码（边糊，属降级）、没有 `matte_b64`=画面里没人。再跑 `tests/test_matte_policy.py`（本机也能跑）确认策略没坏 |
| 抠像耗时忽然变两三倍 | 正常现象：主路（裁切）没找到人时会**再跑一路整幅**，两次都记进 `matte_ms`。要确认是不是每张都在跑两路，看 `/tmp/booth.log` |
| 性能不达标 | 跑 `tests/e2e_test.py`，它会打印中位耗时与理论吞吐 |

**任何一层挂了都不许让参会者空手离开**：走降级路径照常出图，并如实标 `degraded`。

## 9. 已知限制（诚实清单）

1. **编号与统计来自本机**，不跨设备汇总；活动结束手工导出。
2. **并发为串行**：同一时刻只处理一张。现场单人流程够用；上双工位要一工位一进程。
3. **未做 HTTPS 与鉴权**：仅限可信内网。要公网暴露必须加认证反代。
4. **不做人脸识别、不做身份比对**，只做「人像分割」—— 这是合规上的关键区分，对外口径必须一致。
5. **小红书 / 微信没有开放第三方一键发布接口**，所以取图页给的是「保存原图 + 现成文案」，
   不是「一键分享」。
6. **大屏「最近成片」会滚动展示前一位参会者的照片**，属于现场公示口径；
   若要更稳，可在拍摄位明确告知。
