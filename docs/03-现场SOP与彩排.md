# 装置5 · 现场 SOP 与彩排

## 1. 人员配置

| 角色 | 人数 | 职责 | 为什么不能省 |
|---|---:|---|---|
| 引导/拍摄操作员 | 1 / 班次 | 喊人、指导站位、判断重拍、勾同意、按键 | 「摆个牌子自助」在现场会变成无人使用或秩序混乱，两种情况都浪费预算 |
| 取图/贴纸发放 | 0.5–1 | 指导扫码、补发贴纸、处理取图失败 | 取图是最容易卡住的环节，卡住就堵住出口 |
| 装置负责人（Plan A 指定） | 1 | 设备、系统、故障处置、与主办对接 | 需求明确要求指定 1 名 |
| 合规/数据责任人 | 1（可兼） | 同意记录、删除请求、留存到期清理 | 有删除请求时必须有明确的人执行 |

**班次建议**：每人连续值守不超过 2 小时。展会现场 6 小时单人值守，
后半程的引导质量会明显下降，队伍会断。

## 2. 节拍目标

| 环节 | 目标 | 累计 |
|---|---:|---:|
| 引导入场 + 勾同意 + 选风格 | 10 s | 10 s |
| 拍摄（含 1–2 次重拍） | 15 s | 25 s |
| 生成（推理 0.2–1 s，可忽略） | 10 s | 35 s |
| 取图 + 领贴纸 | 20 s | **55 s** |

**优化后目标 35 s/人 → 约 100 人/小时。**
关键优化点：取图二维码提前贴好、生成期间口头说明、拍摄位与取图位分开。

单工位两天各 6 小时 = 12 小时，理论上限约 1200 人；实际有排队断流，取 60–70%，
**保守按 800 人排产**。若期望覆盖人数超过 800，必须上第二工位或接受长队。

## 3. 现场流程（每次循环）

```
1  引导      确认下一位站到地贴脚印上；把限位标（手举牌）递到手里
2  合规      指提示牌 → 勾选「合规确认」→ 口头确认一句「本地处理，不联网，不做人脸识别」
3  选风格    问一句「线框 / 蓝图 / 故障？」——把选择权交给参会者，参与感来自这里
4  拍摄      报「3、2、1」→ 按拍摄 → 不立刻说「好了」，先看屏
5  看算力    ★ 指大屏：「看，AI 核在认你的轮廓」——这一步是整个装置的价值所在
6  出图      成片上屏，念编号「第 0471 位见证者」
7  取图      引导到取图位 → 扫二维码 → 教「长按保存图片」
8  发贴纸    贴纸上手，口头一句「欢迎发小红书 #SpacemiTDevCon」
9  送走      请从侧面离场，为下一位腾位
```

**第 5 步不要跳。** 跳过它，这个装置就退化成一台普通拍照机，
和「芯片公司」没有任何关系。整个装置的差异化就在这一步。

## 4. 彩排清单（★ 最重要的部分）

彩排不是「跑一遍看看」，是**逐项签字确认**。以下每一项都要有人负责、有结果记录。

### A. 硬件

- [ ] 背景板稳固，3m 宽幅无晃动（用力推一下）
- [ ] 道具墙固定，不会被碰倒
- [ ] 三盏灯全部点亮，色温一致，无频闪可见
- [ ] 灯架沙袋已挂
- [ ] 相机位固定，构图经真人确认（头顶留空、脚部不被裁）
- [ ] 地贴定位标已贴，站在上面构图正确
- [ ] 全部电线入线槽/贴地固定，**用手拉一下不松动**
- [ ] 供电分路：灯组一路、IT 设备一路
- [ ] 大屏亮度足够（展厅灯光下可读）

### B. 软件

- [ ] `python tests/test_qr.py` 全绿
- [ ] `python tests/e2e_test.py --base http://<地址>:8090` 全绿
- [ ] **后端确认是 `worker` 不是 `mock`**（操作员面板看徽章，MOCK 会显黄标）
- [ ] 操作员面板「现场检查清单」显示全部通过
- [ ] 拍摄位浏览器能开摄像头（不是开发机，是现场那台操作终端）
- [ ] 大屏自动刷新正常
- [ ] 服务已配 systemd 开机自启，**断电重启后能自动恢复**

### C. 效果（必须真人和真机，不能用合成图）

- [ ] 三种风格各拍一次真人，逐张看边缘：头发、眼镜、深色衣物、与背景接近的肤色
- [ ] 强光/逆光下各拍一次，确认不会整体失败
- [ ] 两人同框一次，确认只保留最大目标（设计如此）
- [ ] 背景无人时拍一次，确认走降级路径照样出图
- [ ] 成片在**手机相册缩略图**下看一次（社交传播的真实观看场景）

### D. 链路与降级

- [ ] **拔网线**，完整跑一遍拍摄→取图，确认离线可用
- [ ] 拔掉 K3 电源再上电，确认服务自愈且历史照片仍在
- [ ] 手动杀掉推理进程，确认：① 下次拍摄走降级出图 ② 「重建推理后端」能恢复
- [ ] **真手机扫二维码**（至少 iOS + Android 各一台）——开发机的解码器通过
      不等于手机能扫，这是两个完全不同的验证
- [ ] 手机扫码 → 保存到相册 → 确认图片质量可接受（不是糊的）
- [ ] 取图页「复制分享文案」在小红书/微信输入框里能正常粘贴

### E. 合规

- [ ] 提示牌在**排队起点**可见（不是拍摄位）
- [ ] 同意勾选框可用，未勾时拍摄按钮确实被禁用
- [ ] 删除功能实测：取图页自助删除 → 文件确实从磁盘消失
- [ ] 数据留存期限已确认，且有人负责到期清理
- [ ] 未成年人提示在场

### F. 吞吐压测

- [ ] **连续 20 人**无人工干预（除引导）跑通，记录：总耗时、中位耗时、失败数
- [ ] 中位耗时 ≤ 35 s 达标；不达标就找瓶颈（通常是取图环节）
- [ ] 失败率 = 0
- [ ] 连续 2 小时不重启服务，观察内存与温度

> `20 人`这个数字是**建议起点**，不是拍脑袋：它足以暴露队列、耗材、
> 人员疲劳这三类问题，又不至于占用过多彩排时间。若彩排当天人多，
> 用 50 人更保险。这个值应在彩排前由负责人确认并写进验收记录。

## 5. 验收标准

| 项 | 标准 | 实测（彩排回填） |
|---|---|---|
| 中位完成时间 | ≤ 35 s | |
| 单工位吞吐 | ≥ 100 人/小时 | |
| 端到端成功率 | ≥ 98% | |
| 连续压测失败数 | 0 | |
| 断网可用 | 100% 通过 | |
| 二维码真机可扫 | iOS + Android 均通过 | |
| 删除后文件消失 | 100% | |
| 高风险动作拦截 | 无同意的请求 100% 被拒 | |
| 一键恢复 | ≤ 10 s | |
| 断电自恢复 | ≤ 3 min | |

**未达标的项不许「先上再说」。** 现场没有工程师的调试时间，
彩排是唯一能改的窗口。

## 6. 应急预案

| 情况 | 处置 |
|---|---|
| 推理持续失败 | 切「降级出图」照常出片（原片 + 水印带），口头说明「AI 部分今天休息」；**不许假装 AI 在工作** |
| K3 完全挂了 | 换备用机（整盘镜像）；没有备用机则切「纯拍照 + 水印」模式（把 backend 设 mock 会显示 MOCK 徽标，不诚实；正确做法是停掉推理并在告示上说明） |
| 排队过长 | 简化流程：跳过风格选择，只用默认风格；引导时先统一说明合规，不逐人勾选（但**必须**能证明已告知） |
| 摄像头坏了 | 切「文件」通道上传；或用操作员手机拍后上传 |
| 打印机卡纸 | 数字照片是主交付，打印是限量——直接暂停打印，不阻塞主流程 |
| 贴纸发完 | 记录编号，承诺寄送；或改为「扫码领取电子徽章」（需提前准备） |
| 参会者要求删除 | 操作员面板按编号删除 → 向本人确认 → 记录在案 |
| 未成年人要求拍摄 | 必须有监护人代同意，否则不拍 |

## 7. 撤展与收尾

- [ ] 停止服务（先停服务再断电，避免状态文件写坏）
- [ ] 导出统计：完成数、成功率、AI 核占比、中位耗时（**不含人脸图**）
- [ ] 按留存期限处理照片；若活动结束即删，**保留删除记录备查**
- [ ] 清点电子设备（对照运输箱清单）
- [ ] 拆装背景板/道具墙，按编号装回箱
- [ ] 复盘一页纸：实际吞吐、故障次数、参会者反馈、下次要改什么

## 8. 复盘要收集的数据

装置的价值要用数字说话，收尾时至少留下：

| 指标 | 来源 |
|---|---|
| 完成张数 / 到场人数 | 系统 `serial` 与主办口径 |
| 成功率、降级率 | 操作员面板 |
| 中位耗时、AI 核占比、平均推理耗时 | 操作员面板 |
| 扫码取图率（有多少人真的打开了取图页） | 需加取图页访问计数（**当前未实现**，见下） |
| 实际传播量（#SpacemiTDevCon 话题） | 会后人工统计 |
| 故障次数与恢复时间 | 审计事件 `events.jsonl` |

> **当前缺口**：系统记录了「出图」但**没有记录「取图页被打开」**。
> 传播转化率是本案的关键成效指标之一，建议在彩排前补一个取图页访问计数
> （`GET /p/{id}` 里计一次）。这是小改动，但决定会后能不能拿出传播数据。
