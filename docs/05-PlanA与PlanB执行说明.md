# 装置5 · Plan A 与 Plan B 执行说明

> 用户需求里 Plan A / Plan B 各只有一句话，缺少可执行内容。
> 本文件把它们落成：做什么、谁负责、边界在哪、什么条件下放弃。

---

## Plan A · 把 K3 的实际使用体验融入拍照互动

需求原文：

> 在基础方案上扩充，将 K3 芯片的实际使用体验融入拍照互动环节，需指定 1 名负责人推进。

### A.0 负责人（需求明确要求，先填这一栏）

| 项 | 内容 |
|---|---|
| 负责人 | ⛔ **待指定** |
| 备份负责人 | ⛔ 待指定 |
| 决策范围 | A1/A2/A3 取舍、技术方案变更、工期取舍 |
| 对接对象 | 品牌（物料）、法务（合规）、主办（场地供电） |
| 汇报节奏 | 每周期一次进度 + 风险 |

**没有负责人就不启动 Plan A。** 一句话需求 + 无主，必然变成"谁都在做、没人负责"。

### A.1 三个候选玩法（详述见 `../01-玩法设计与用户旅程.md` §4）

| 项 | 内容 | 成本 | 风险 | 建议 |
|---|---|---|---|---|
| **A1 算力可见** | 大屏显示人像掩码逐像素成形 + `EP SpaceMIT` 徽章 + 单帧耗时读数 | **已实现** | 低 | ✅ **必做** |
| **A2 提示词即玩法** | 屏上选风格/提示词，动态模型实时切换，同一人产出多种版本 | 低–中 | 中 | ✅ **建议做**（见下方限制） |
| **A3 证件照签发流水线** | 用 yolos-box 的 MCP 17 工具串「拍摄→分割→合成→登记→编号→查询链接→名册大屏」 | 中–高 | 中高 | ⚠️ 视剩余工期 |

### A.2 当前实现状态（不吹不藏）

| 能力 | 状态 |
|---|---|
| A1 掩码大屏 + EP 徽章 + 耗时 | ✅ **已实现并测试**（`static/stage.html`，服务上报真实 `ep_effective` 与 `model_ms`） |
| A1 见证者名册滚动 | ✅ 已实现 |
| A2 三种风格实时切换 | ✅ 已实现（风格在渲染侧，切换零延迟） |
| A2 **任意提示词实时生效** | ⚠️ **未实现**。当前用烘焙模型，提示词只能选烘焙时已有的类。要做任意提示词，需接入 K3 本地文本编码（内部探针脚本，未随仓库发布）为动态模型提供 `text_embeds` —— **这是一项额外开发工作量，尚未验证** |
| A3 编号 + 查询链接 | ✅ 已实现（编号、取图页、二维码） |
| A3 登记入册 / MCP 编排 | ⚠️ 未实现（编号即"入册"，但未接 yolos-box 的 MCP 工具链） |

> **给负责人的一句实话**：A1 已经做完，你现在就能用。
> A2 的"改一行字换一类目标"是需要额外开发才能兑现的能力，
> 不要在对外材料里把它写成已有功能。

### A.3 执行步骤

1. **指定负责人**，回填 A.0。
2. **确认 A1 的呈现节奏**：`STAGE_REVEAL_HOLD_MS`（默认 1600ms）。
   这是**呈现节奏**的延后，屏幕上所有数字都是真实读数，不伪造计算。
   现场若觉得拖节奏，调到 0 即可关闭。
3. **决定 A2 是否投入**：若要做任意提示词，先做一个最小验证——
   在 K3 上跑通 `k3_text_pe.produce_text_embeds(["person"])` 并把结果喂给
   `model_test_worker`（它已支持 `text_embeds` 入参）。这一步半天能验证完，
   **验证通过再排期**，不要先承诺。
4. **决定 A3 是否投入**：A3 的收益是"证明这块芯片跑得动一个 Agent"，
   叙事价值高；代价是需要真正开发工作量。若工期紧，**先保 A1+A2**。
5. **每个周期产出可演示增量**，不要攒到最后一起演示。

### A.4 退出条件（什么情况下放弃 Plan A）

- 基础方案（L0：拍照+水印+取图+贴纸）未达标 → **先保基础方案**，Plan A 全部延后
- 彩排中 A1 的掩码显示不稳定 → 降级为只显示 EP 徽章与耗时（信息量少但仍真实）
- 推理后端在现场不可靠 → 退到 L0，并如实说明"AI 部分今天不可用"，
  **不许假装 AI 在工作**（把 backend 设成 mock 会在大屏显示 MOCK 徽标，
  这是刻意的诚实设计）

## Plan B · 邀请黑客松拍照机 Demo 团队到场

需求原文：

> 邀请黑客松中的拍照机 Demo 团队到场参展，由联络负责人对接协调。

### B.0 联络负责人

| 项 | 内容 |
|---|---|
| 联络负责人 | ⛔ **待指定** |
| 候选团队名单 | ⛔ 待提供（是否已有候选？是否已接触？） |
| 对接截止时间 | ⛔ 待定（需早于物料定稿，否则品牌位/电源排不进去） |

### B.1 必须在对接时谈定的六件事

这份清单是这条线的核心。不谈这六条，展位会变成一个"谁来都行"的摊位。

| # | 议题 | 我方的立场建议 |
|---|---|---|
| 1 | **交付边界** | 明确他们提供什么：硬件？软件？只是人？还是整套装置？缺一项就要写清谁补 |
| 2 | **是否必须跑在 K3 上** | **这是关键**。若他们的 Demo 跑在 x86/ARM 上，那这个展位与"进迭时空开发者大会"的主线无关，只是租了个位置。建议：**要求至少一个环节在 K3 上运行**，否则降级为"生态伙伴展示位"，不与装置5 并列宣传 |
| 3 | **拍摄数据归属** | 他们拍的参会者照片归谁？存哪？多久删？**必须适用同一套合规标准**（§见 `04-合规与现场文案.md`）。若他们用自己的云端服务，合规风险由谁承担要写清 |
| 4 | **知识产权归属** | Demo 代码/设计的 IP 归属；大会后我方能否继续使用或参考 |
| 5 | **我方提供的资源** | 场地面积、电源（几路、多少瓦）、网络、品牌位、宣传口径。**电源是最容易起争议的**——如果他们带大功率设备，要提前算总功率 |
| 6 | **对外口径** | 联合展示还是独立展示？宣传物料上怎么署名？谁对媒体发言？ |

### B.2 两种接入模式

| 模式 | 我方投入 | 风险 | 建议场景 |
|---|---|---|---|
| **联合展位**（同一 3m×3m，装置5 + 他们的拍照机） | 分摊空间与电源 | 动线可能冲突；两个装置抢同一批人流 | 空间紧张、且对方 Demo 与拍照强相关 |
| **独立展位**（相邻但分开） | 独立空间与电源 | 成本高；人流分散 | 对方 Demo 主题不同（如机器人、Agent） |

**建议优先独立展位。** 两个拍照类装置放一起会互相抢人，而且一旦对方出故障，
会连带影响我方装置的口碑。

### B.3 时间线要求

```
T-45 天   确认候选团队、明确是否接触过
T-30 天   谈定 B.1 六项；签署或至少书面确认
T-21 天   确定展位模式与电源需求，报主办
T-14 天   对外口径与物料定稿（联合署名需要品牌审核）
T-7 天    联合彩排（若联合展位，必须联合彩排一次动线）
```

⛔ **若 T-30 天仍未谈定，建议放弃 Plan B**，把资源投入装置5 的第二工位。
理由：临期确定的第三方参展，是现场事故的高发来源。

### B.4 退出条件

- 对方无法保证 Demo 在 K3 上运行 → 降级为纯生态展示，不并入装置5 宣传
- 对方数据流向不合规（例如上传到自有云端且不愿调整）→ **不接**
- T-30 天未谈定 → 放弃，转投第二工位

## 附：两个 Plan 的关系

Plan A 和 Plan B **不冲突，但不建议同时上**。

| 组合 | 效果 | 资源 |
|---|---|---|
| 只做基础方案 | 达标但无差异化 | 低 |
| 基础 + Plan A（A1） | **推荐**：差异化成立，成本几乎为零 | 中 |
| 基础 + Plan A（A1+A2+A3） | 叙事最强 | 高，需工期 |
| 基础 + Plan B（独立展位） | 生态感强 | 高，且引入外部依赖 |
| 三者全上 | 现场复杂度陡增 | 很高，**不建议** |

**建议：基础方案 + Plan A 的 A1（已实现）。**
A2/A3 与 Plan B 按剩余工期与预算，**逐个决策，不打包承诺**。
