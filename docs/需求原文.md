- **MJPG**：3840x2160 / 3264x2448 / 2592x1944 / 2048x1536 / 1920x1080 / 1600x1200 / 1280x720 / 640x480，**全部 30 fps**

- 实测抓帧（OpenCV `CAP_V4L2` + MJPG，含预热）：4K 1.18s / 2592 0.94s / 1080p 0.69s，帧内容正常
- **结论**：服务端抓帧（OpenCV V4L2）是唯一正确路径。浏览器 getUserMedia **不可用**（相机挂在 K3 上）

### 2.2 ★ 最重要的发现：AI 核只加速「量化」模型

SpaceMIT EP（`SpaceMITExecutionProvider`，`import spacemit_ort` 生效）在同一台机器上的实测：

| 模型 | 精度 | CPU p50 | SpaceMIT EP p50 | 加速比 |
|---|---|---|---|---|
| `yolov8n.q.onnx`（官方 demo） | INT8 | 467.1 ms | **9.5 ms** | **49×** |
| `yolov8s.q.onnx`（官方 demo） | INT8 | 1108.1 ms | **16.5 ms** | **67×** |
| `yoloe26s-seg-prod.onnx`（旧项目引用） | FP32 | 956.4 ms | 540.0 ms | 1.8× |
| `yoloe26s-seg-dynamic.onnx`（旧项目引用） | FP32 | 1030.0 ms | 1052.9 ms | **1.0×（无效）** |

**这条推翻了一个此前被当作结论的说法。** 旧知识库（`knowledge/02-技术底座-可引用实测.md`）
写「EP 约 1.3–1.9×、0.22 s/帧」。实测：FP32 模型上 EP **基本不加速**，
真加速只发生在 INT8 量化模型上，且量级是 **10–70×**，不是 1.x×。
→ **凡是要展示「算力」，就必须用量化模型。** 这条直接决定叙事与选型。

### 2.3 已下载并跑通的量化 + 开放词汇 + 分割模型

来源：SpacemiT 官方模型仓 `spacemit-com/model-zoo-vision`，CDN `archive.spacemit.com`。

`yoloe-v8s-seg.dynq.onnx` 的 I/O（实测）：
```

in  txt_feats   [1, 80, 512]      tensor(float)     <- 80 个词槽，未用到的填 0
out output0     [1, 116, 8400]    tensor(float)     <- 4 box + 80 cls + 32 mask 系数

```
`mobileclip.q.onnx`：`in input_ids [seq_len, 77] int64` → `out [seq_len, 512] float`
（tokenizer = 标准 CLIP BPE，K3 上已有 `/opt/yolos-box/data/models/bpe_simple_vocab_16e6.txt.gz`
与 `/opt/yolos-box/python/text_tokenizer.py` 的 `CLIPTokenizer`）

**端到端实测**（`prompts=["person"]`，1280x720 街景真图）：
- 推理 **p50 = 176.5 ms**（5.7 FPS），首帧 1022 ms（含 EP 预热），p90 出现 1024 ms 抖动
- 正确输出 **6 个人**，score 0.29–0.76
- **人像 mask 正确成形**（可视图已人工确认：干净的多人剪影）
- 文本编码可缓存（同一词表只算一次）

### 2.4 硬约束：cv2 与 spacemit_ort 不能同进程

来源：`/opt/yolos-box/python/yoloe_worker.py` 注释 + 官方写法：
> `onnxruntime` 必须**先于** `spacemit_ort` import；反过来会
> `Attempt to use DefaultLogger but none has been registered`。
> 且 **cv2 与 spacemit_ort 同进程会导致 import-order 崩溃**（OpenCV 的共享库栈破坏 ORT 日志管理器）。

**→ 架构硬约束：抓帧进程（cv2）与推理进程（spacemit_ort）必须分离，用子进程 + 行式 JSON IPC。**
这条不是风格选择，是崩溃与不崩溃的区别。

### 3.2 从知识库继承、必须遵守的纪律（`knowledge/04-踩坑与教训.md` 摘要）

1. **先量，再判断。** 不要凭「看起来」下结论（已有 5 次因此做错方向）。
2. **判据本身也要验证。** 指标写错比没有指标更糟（已有 4 次「指标骗人」）。
3. **设计约束要由代码保证，不靠自觉。**「尽量避开照片区」会失效，「压到就抛异常」不会。
4. **不猜意图。** 读不出来就直接问，并给出可选项。
5. **诚实优先。** MOCK 要显示黄标；降级要标 `degraded`；大屏耗时与 EP 徽章必须是真实读数。

### 3.3 规格变更史（会重演，必须记住）

- 视觉规格从**浅色**改为**暗调**，但**只改了卡片背景这一层**。成片风格 / 界面 / 分享图 / 水印带
  仍是浅色，成品是「暗调卡片 + 浅色成片 + 浅色界面」的混合体，**视觉上不成立**（见 `docs/` 视觉规格）。
- 本轮 UI 要**一次性从暗调令牌出发**，不要再出现分层不一致。

### 3.4 合规红线（`docs/04-合规与现场文案.md`）

- 人脸是**敏感个人信息**：单独同意、明示目的与期限、提供删除入口、不得未经同意对外使用。
- 未成年人肖像需监护人同意。
- **RISC-V 是 RISC-V International 注册商标**；**K3 die shot 必须官方授权**，不得用网络抓取图。
- 小红书 / 微信**没有**对第三方开放的一键发布接口。只能做「扫码取图 + 现成文案」。
- 摄影灯对光敏人群的影响需在提示中说明。

- 不做 App / 小程序；不做全自动无人值守；不做人脸识别（只做人像分割）。
- 不承诺一键发布；不承诺影楼级抠像；不依赖现场 Wi-Fi 或公网。
