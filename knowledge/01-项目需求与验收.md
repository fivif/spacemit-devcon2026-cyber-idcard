# 01 · 项目需求与验收

## 1. 需求原文（逐字，不得改写）

### 📸 装置 5：赛博开发者证件照

**基础方案（最低交付标准）**

- **场景搭建**：设置一个 3m×3m 的品牌拍照区。背景板采用 K3 芯片 die shot 的巨幅风格化视觉，并搭配「SpacemiT DevCon 2026」Logo。道具墙陈列 RISC-V 指令集符号手举牌、芯片晶圆道具和代码屏风。
- **打卡玩法**：参会者在拍照区拍摄 1 张打卡照，即可领取「开发者见证者」徽章贴纸。
- **社交传播**：支持现场即拍即传，照片自动添加 #SpacemiTDevCon 水印，可一键分享至小红书或朋友圈。
- **物料清单**：背景板、道具墙、摄影灯 3 盏、拍立得 1 台、即时传图系统。

**备选升级方案**

- **Plan A**：在基础方案上扩充，将 K3 芯片的实际使用体验融入拍照互动环节，需指定 1 名负责人推进。
- **Plan B**：邀请黑客松中的拍照机 Demo 团队到场参展，由联络负责人对接协调。

## 2. 规格变更史（★ 最容易出错的地方）

本项目**规格在过程中变更过**。不知道变更史就会按作废的规格干活。

| 时间点 | 变更 | 谁定的 | 影响 |
|---|---|---|---|
| 立项 | 底色未指定 | — | — |
| 第 N 轮 | **浅色风**（「白天开的，我要浅色风，场景要真实，写实」） | 用户 | 整套 UI + 成片改为浅色 |
| 第 N+1 轮 | 背景板改为**横版**、要**炫酷** | 用户 | 六套横版重新设计 |
| 第 N+2 轮 | 要求**姓名 + RISC-V 文字内容** + 不要单调 | 用户 | 新增 `riscv.py`；水印带加姓名行 |
| 第 N+3 轮 | 照片**放左下**、不要放中间、**完全重新设计** | 用户 | 版面重做；引入几何守护 |
| 第 N+4 轮 | **「A 证件照不要浅色」** —— 撤销浅色风，改**暗调** | 用户 | 六套改为暗调高对比 |
| **当前** | 指定 `image_2_1.png` 为**背景基础图**；**搭知识库，暂不实施** | 用户 | 见 `00-参考底图-规格书.md` |

## 3. 硬约束（不可协商）

### 3.1 合规（红线）

| 项 | 要求 |
|---|---|
| 人脸信息 | 属**敏感个人信息**。需单独同意、明示目的与保存期限、提供删除入口 |
| 肖像使用 | 未经同意不得用于对外宣传物料 |
| 未成年人 | 需监护人同意，提示牌必须覆盖 |
| **能力边界** | **只做人像分割，不做人脸识别 / 人脸库 / 身份比对**。这是对外口径必须守住的线 |
| 商标 | **RISC-V 是 RISC-V International 注册商标**，使用需符合其商标政策 |
| 素材授权 | **K3 die shot 必须来自官方授权素材**，不得使用网络抓取图 |
| 数据留存 | 默认 7 天（`retention_hours: 168`），须有明确责任人执行删除并留记录 |
| 光敏人群 | 若用频闪灯需在提示中说明 |

### 3.2 场地与网络

| 约束 | 说明 |
|---|---|
| 面积 | 3m×3m 标准展位 |
| **不得依赖现场 Wi-Fi** | 装置必须**离线可用**（这同时是叙事：「断网也能跑，因为算力在芯片上」） |
| 供电 | 摄影灯与 IT 设备**分路供电**（灯组开关瞬间会造成 K3 掉电重启） |
| 走线 | 3m×3m 内是人员密集走动区，**电线必须入线槽/贴地固定** |
| 摄像头 | K3 板载**无采集设备**（`/dev/video0` 是 M2M 编解码节点）→ 必须外接 USB UVC 或外部相机 |

### 3.3 平台能力边界（技术事实，不是选择）

| 需求原文 | 实际能做到 | 说明 |
|---|---|---|
| 照片自动加 `#SpacemiTDevCon` 水印 | ✅ 能 | |
| 现场即拍即传 | ✅ 能 | 局域网扫码，不依赖公网 |
| 「**一键分享至小红书或朋友圈**」 | ❌ **做不到** | 两个平台都**没有对第三方开放的发布接口**。微信只在「内置浏览器 + 认证公众号 + JS-SDK 签名」下开放分享，且分享的是**链接卡片**，不是照片本体 |
| 「一键**保存**」/「一键**复制**文案」 | ✅ 能 | 这是能做到的极限：预裁比例 + 现成文案 |
| 一键**唤起** App | ⚠️ 部分 | URL scheme 可唤起；能否落到发布页由 App 决定 |

**对外口径要求**：不得宣称"一键发布到小红书/朋友圈"。详见 `../docs/06-社交传播与分享边界.md`。

## 4. 验收标准

| 指标 | 目标 | 备注 |
|---|---|---|
| 标准流程中位时长 | ≤ 35 s / 人 | 从入场到取图 |
| 单工位吞吐 | ≥ 100 人/小时 | 优化后目标 |
| 端到端成功率 | ≥ 98% | |
| 断网可用 | 100% | |
| 高风险拦截（无同意的请求） | 100% 被拒 | |
| 二维码真机可扫 | iOS + Android 均通过 | 独立解码器通过 ≠ 手机能扫 |
| 删除后文件消失 | 100% | |
| 拿号到取图，照片区内不得有底纹 | 见 `03-视觉规格-暗调.md` §3 | |

**吞吐估算（单工位）**

| 环节 | 秒 |
|---|---:|
| 引导入场 + 勾同意 + 选风格 | 10 |
| 拍摄（含 1–2 次重拍） | 15 |
| 生成（推理 0.2–1s，可忽略） | 10 |
| 取图 + 领贴纸 | 20 |
| **合计** | **≈ 55（优化后 35）** |

两天各 6 小时 = 12 小时，理论上限约 1200 人；实际有排队断流，取 60–70%，
**保守按 800 人排产。超过 800 人必须上第二工位或接受长队。**

## 5. 技术选型决策（已定）

| 决策 | 内容 | 理由 |
|---|---|---|
| D1 | 复用 **yolos-box** 的推理组件，不另造 | K3 上已跑通（`model_test_worker.py` + `yoloe26s-seg-prod.onnx`） |
| D2 | 控制面用**纯标准库 Python**，端口 8090 | K3 上无需 pip / node / 构建步骤 |
| D3 | 前端**原生 HTML/JS**，无 CDN 无框架 | 离线可用；断网不掉字 |
| D4 | 二维码**自研纯 Python** 实现 | 离线；无第三方库许可问题 |
| D5 | 风格化优先于抠像精度 | YOLOE-26 是开放词汇分割模型，不是商用抠像模型。用**风格吸收边缘瑕疵** |
| D6 | 三层降级（L0 拍照出水印 / L1 推理合成 / L2 编号名册） | 现场推理服务挂掉是常态；**下层不依赖上层** |
| D7 | 推理失败**照常出图**并标记 `degraded` | 参会者不该空手离开 |
| D8 | MOCK 后端在界面上**显式标注** | 不冒充真机 |
| D9 | 照片位置与内容避让由**几何守护**强制 | 见 `03` §3 |
| D10 | 不实施 Plan A 的 A2/A3 与 Plan B 之前，先保基础方案 | 基础方案是"最低交付标准" |

## 7. 三层降级设计（现场纪律）

| 层 | 内容 | 挂了会怎样 |
|---|---|---|
| **L0 保底** | 拍照 → 水印 → 扫码取图 → 领贴纸 | 唯一必须永远可用的层 |
| **L1 主交付** | K3 推理 + 风格化合成 + 大屏显示掩码/EP/耗时 | 退化为 L0，**标记 degraded 照常出图** |
| **L2 加分** | 编号、名册滚动、查询链接 | 退化为 L1 |

**这不是过度设计，是现场纪律。** 展会现场推理服务挂掉是常态，
参会者看到的只会是"这个展位坏了"。L0 独立可用是把"事故"变成"功能降级"的唯一办法。
