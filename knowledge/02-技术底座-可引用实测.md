## 2. 推理能力（本项目的核心依据）

| # | 事实 | 值 | 等级 |
|---|---|---|---|
| 10 | **YOLOE-26 开放词汇分割（AI 核 / SpaceMIT EP）** | **0.22 s/帧**（n 档）· 0.54 s（s 档） | [实测] |
| 11 | **同模型纯 CPU 对照（`yoloe-v8s-seg.dynq.onnx`，640x640）** | **1157.5 ms/帧**（中位 7 次） | [实测 2026-09-14] |
| 12 | **SpaceMIT EP 相对纯 CPU 的加速（本项目部署的模型）** | **5.6×**（EP 205.9 ms vs CPU 1157.5 ms，同一份输入、同一台机器、只换 provider） | [实测 2026-09-14] |
| 12b | AI 核线程数 | 4（`SPACEMIT_EP_INTRA_THREAD_NUM=4`）；申请更多会被 EP「答应下来但跑得极慢」 | [实测] |
| 13 | 动态提示词模型 | `yoloe26s-seg-dynamic.onnx`（47.3 MB），**改提示词无需重新导出模型** | [实测] |
| 14 | 生产模型 | `yoloe26s-seg-prod.onnx`（41.7 MB，opset19，烘焙 `set_classes`） | [实测] |
| 15 | **INT8 量化** | 31.8 ms/帧，相对 FP32 **7×**，真帧 IoU **0.953–0.954** | [实测] |
| 16 | INT8 配方 | ORT `quantize_static` QDQ，per-channel=True，`QuantizeBias=False`，YOLOE 需排除 `ffn/ffn.1/conv/` | [实测] |
| 17 | 多路监控 | 4 路并发，每路约 **5 FPS**（1–12 路可配） | [实测] |
| 18 | 端到端 | 真实数据训练的分割模型 **mAP50 ≈ 0.75** | [实测] |
| 18b | **人像抠像（matting）模型 MODNet**（25.9 MB，256×256 输入） | **266 ms/帧（纯 CPU）** | [实测 2026-09-14] |
| 18c | 抠像候选模型对照（同机、同图、纯 CPU） | `rmbg14` 1024² **7987 ms** · `u2net_human_seg` 320² **3044 ms** · **MODNet 256² 266 ms** | [实测 2026-09-14] |
| 18d | 抠像给每张成片增加的耗时 | 整幅直出 **+260 ms**；整幅没找到人、走「按人裁切重试」时 **+520 ms** | [实测 2026-09-14] |
| 18e | **抠像模型上不了 AI 核** | MODNet 的 BatchNormalization 让 SpaceMIT EP **编译失败并硬崩**（`operator compile failed at node (BatchNormalization_197)`），整个 worker 进程直接死 | [实测 2026-09-14] |
| 18f | **抠像必须整幅直出** | MODNet 对输入裁切极敏感：同一张图只改裁切起点，覆盖率 0.268 → 0.020；整幅反而稳 | [实测 2026-09-14] |

**抠像为什么值这 260 ms**：分割模型给的是「框 + 框内多边形」，边是折线、发丝全丢 ——
拿它当抠像，成片里的人像是从一块方形框里挖出来的。MODNet 逐像素给软 alpha，
头发丝和半透明边缘都在。它是本项目**唯一跑在 CPU 上**的模型，也是唯一**不占 AI 核**的模型：
8 个线程槽全留给分割（seg=4 / det=2）。

> **关于 1.3× / 1.9×（2026-09-14 已作废）**：那两行是别的模型、别的机器上量的，
> 被本项目引用过一次。**对外只用上面第 12 行的 5.6×**，并且要说明它是
> 「同一个分割模型只换 provider」的干净对照 —— 数字小一点，但它经得起追问。
>
> 复现方式（K3 上跑；先停掉 8090 服务，AI 核是独占资源）：
> 用 `app/infer/worker.py` 的 `_session()` 分别建 `SpaceMITExecutionProvider`
> 与纯 `CPUExecutionProvider` 两个会话，喂同一份 `_letterbox` 后的输入，
> 各跑 7 次取中位。

## 4. 必须在代码里遵守的纪律（踩过坑的）

| # | 纪律 | 原因 |
|---|---|---|
| 24 | **不要 `kill -9` 推理进程** | 会泄漏 TCM block（8 块共享 AI 核内存），此后所有推理必失败 |
| 25 | EP 推理前先查 TCM；发现 busy 且 PID 不存在 → `spine_tcm_runtime_mem_force_release(0)` | 恢复被 stale block 占住的 AI 核 |
| 26 | **不要在同进程 `import cv2` 后用 spacemit_ort** | 触发 `DefaultLogger` 崩溃。worker 改用 PIL/numpy |
| 27 | **必须用系统 py3.14**（`/usr/bin/python3`） | `.venv` 的 py3.12 **没有 riscv64 的 onnxruntime wheel** |
| 28 | 先 `import onnxruntime` 再 `import spacemit_ort` | 顺序反了触发同一条 DefaultLogger |
| 29 | `provider_options` 的值必须是**整数字符串** | 传 `"false"` 会触发 EP `stoi` 异常 → **静默回退 CPU**（不报错但没走 EP） |
| 30 | 判断是否真走 EP：看 `sess.get_providers()` + 计时 | 0.22s 是 EP；0.3s 是 CPU |
| 31 | K3 与 worker-pack **必须同步部署** | 旧 worker 遇 `device=auto` 会响亮失败（`Invalid CUDA 'device=auto'`） |
| 32 | riscv64 上 PyPI 几乎无预编译轮子 | 走 dpkg 提取路线 |
| 33 | **抠像模型只能走 CPU**（`_session(..., cpu_only=True)`） | 见 18e：上 EP 是**硬崩**，不是慢 |
| 34 | **不要拿检测掩码当抠像** | YOLOE 给的是「框 + 框内多边形」，边是折线、发丝全丢 —— 成片里的人像会像从一块方框里挖出来的 |
| 35 | 检测框只用来决定「看哪儿」，**不作为最终的边**；裁切重试的结果要与检测掩码 **IoU ≥ 0.30** 才采纳 | 实测 MODNet 会在某些裁切上给出「非空但全错」的 alpha，只靠覆盖率阈值拦不住 |
| 36 | **同一条资源（相机/串口/文件句柄）读者 > 1 时，必须「单生产者 + 分发」** | 每个 MJPEG 连接各自读同一台相机 = 互相偷帧、两边都卡、CPU 编两份。这类竞争不报错，只变慢（`camera.PreviewHub`） |
| 37 | **恒定的读失败要换句柄，不是重试**（`Camera.recover()`：关掉 → 按 by-id 重解析 → 重开） | USB 重新枚举后 `/dev/videoN` 换号，旧 fd 变成 `deleted`，`read()` 恒 False；`/proc/<pid>/fd` 里能看到 `-> /dev/video1 (deleted)` |
| 38 | **USB 带宽按「最坏一帧 × 标称帧率」做预算**（本链路 USB2 实际 ~35 MB/s） | MJPG 2592x1944@30 ≈ 30~60 MB/s → URB 溢出 → 协议错误 -71 → 设备重新枚举。软件能改的只有分辨率（采样率由相机决定，本机 MJPG 各档只列 30fps） |
| 39 | 抠像**先按人框裁切、整幅只作退路**（`BOOTH_MATTE_FILL=0.80` ≈ 外扩 1.25×） | 六档实测：人占画面高 20%/30%/40%/55%/75%/95% 时，裁切 IoU 0.87/0.91/0.91/0.63/0.76/0.54，整幅只有 0.00/0.20/0.61/0.39/0.70/0.54。展台就是「人小背景大」，整幅等于把人缩没 |
| 40 | 抠像用 **MODNet（256²，CPU ~270 ms）**，不要换更大的 | 同图实测：MODNet 298 ms / u2net_human_seg 1203 ms / rmbg14 3059 ms，覆盖率 0.268/0.274/0.272 —— 边在同一档，贵的只是更慢 |
| 41 | 接口/属性返回值一律 `bool(...)` | Python 的 `and` 返回操作数：`ok and image_source` 会把「开着」变成一个路径，`is True` 立刻挂，进 `/api/state` 更糟 |

### 推理 worker 协议（实测契约）

```
请求  {"model_path": str, "frame": <base64 jpeg>, "conf": float,
       "classes": [str]?, "text_embeds": [[float]]?}
响应  {"width", "height", "detections": [...], "model_ms",
       "preprocess_ms", "postprocess_ms", "ep_effective": "spacemit"|"cpu"}
detection {"class_id", "class_name", "conf", "bbox": [x1,y1,x2,y2],
           "polygon": [[x,y],...] | None}
```

- `polygon` 坐标在**原图空间**（worker 内部已 unletterbox）
- `ep_effective` 是"这一帧实际跑在哪个执行单元上" —— **大屏「算力可见」的数据来源**
- 烘焙模型忽略传入的 `classes`，以 ONNX 元数据里的类名为准
