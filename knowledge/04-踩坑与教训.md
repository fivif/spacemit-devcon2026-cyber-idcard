# 一、渲染管线的 6 个真 bug

## 坑 1 · 整幅渐变抹掉所有已绘内容（影响 6 个设计，最严重）

**现象**：HUD 设计左侧整段指令列**消失**，画面那里是纯纸色。不报错、不告警。

**根因**：`Canvas` 的 paint 是**按登记顺序合成到已绘内容之上**的。
六个设计都先用 `alpha=1.0` 的满幅渐变 paint 出去当纸底，**然后**才画线、写文字。
于是那一幅渐变把所有线条和文字全盖掉了。

**修法**：整幅渐变必须在**构造时**给（`Canvas(..., grad=...)`），不能事后 paint。
若确实是事后叠加的需求，`finish()` 里要按**覆盖面积**把满幅的挑出来先行。

**怎么发现的**：量"该有文字的地方是不是纯纸色"。
关键信号是 **HUD 左侧整段指令消失**——如果只看"图生成成功、没报错"，永远发现不了。

**这一坑的代价**：修完后六套的细节密度普遍**翻了 3–6 倍**
（等距芯片 1.95% → 6.22%，版图特写 3.34% → 19.24%）。
**也就是说，在此之前我交付的 6 套图全都是残废的，而我一直以为它们是好的。**

## 坑 2 · 静默区（避让区）完全失效

**现象**：计算出的"静默区"里，细节**比边缘还高**（比值 1.22，应该 < 0.45）。

**根因**：有符号距离算反了。写成
`sqrt(max(qx0-x, x-qx1)² + max(qy0-y, y-qy1)²)`
—— 区域**内部**的两个差都是负数，平方后又变正，于是"区域内"被当成了"远离区域"。
静默强度在最该压的位置反而最低。

**修法**：用真正的**有符号箱体 SDF**（内部为负、外部为正）：

```python
dx = np.maximum(x0 - xx, xx - x1)
dy = np.maximum(y0 - yy, yy - y1)
outside = np.sqrt(np.maximum(dx, 0.0)**2 + np.maximum(dy, 0.0)**2)
inside  = np.minimum(np.maximum(dx, dy), 0.0)
sdf = outside + inside          # 内部为负
field = np.clip(-sdf / feather, 0.0, 1.0)
```

**这一坑的性质**：图**看着没问题**，只有量像素标准差才查得出。
六张图全部受影响。

## 坑 3 · 数据填充写进功能图形格（二维码编码器）

**现象**：二维码自检全绿，但**真解码器读不出**。

**根因（两处）**：

1. **保留图与占位图混用**：格式信息/版本信息的格子只标了"保留"（reserved），
   没有写入占位值。数据填充用 `m is None` 判断，于是把 45 个数据比特
   写进了定位图形的**分隔符**（3 个 × 15 格），导致其后所有模块**整体错位**。
   → 判据必须用**保留图 `res`**，不能用 `m is None`。
2. **格式信息位序写反**：格式信息是 **MSB 在先**（bit14 在 (8,0)），
   我写成了 LSB 在先。真解码器读到的掩码号与实际施加的掩码不一致。
   版本信息（v≥7）则相反，是 **LSB 在先**。**两处约定不同**。

**修法**：位序由**已知可解的参考矩阵反推**确认，不凭记忆。

**另一处**：容量上限算错了（写成 271 字节，实际 v10-M 是 213 字节）。
容量 = `(数据码字数 × 8 − 模式头位数) ÷ 8`。

## 坑 4 · 星号解包不能跟条件表达式

**现象**：`SyntaxError`，4 处。

```python
c.line(pts, (*INK if long_t else INK_2, 165), width=1)     # ✗ 语法错误
c.line(pts, (*(INK if long_t else INK_2), 165), width=1)   # ✓ 需要额外括号
```

## 坑 5 · 超采样画布上用了最终坐标（漏乘 ss）

**现象**：画出来的东西位置和粗细全错，**不报错**。

**修法**：把缩放收进 `Canvas` 的方法里（`_s()` / `_pw()`），
**调用方无法漏乘**。所有坐标一律用最终尺度传入。

## 坑 6 · Windows 控制台 GBK 把服务挡在启动之前

**现象**：`UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'`。
服务直接起不来。

**修法**：启动时 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`，
并且**不输出 emoji**。

**同类**：`--defer` 加载的脚本在内联脚本之后执行 →
`ShareKit is not defined`。需要同步加载。

# 二、验收指标骗人的 4 次 ★（比 bug 本身更危险）

**验收指标写错，比没有指标更糟 —— 它会告诉你「全部通过」。**

## 谎报 1 · 用「偏离中位色」当"有墨"

**问题**：把**平缓渐变**也算成"有内容"。所以"整幅渐变抹掉文字"（坑 1）
这种 bug，这个指标**查不出来**。它一直报 OK。

**修法**：改用**细节能量** = `|原图 − 高斯模糊(σ=3)|`，只测纹理、不测缓变。

## 谎报 2 · 用裸标准差验收静默区

**问题**：静默权重自身从 0.66 到 0.88 有一条**平缓坡道**，乘到纸色上产生约 12 的 std。
那是空间亮度渐变、人眼几乎看不见，但裸 std 把它当成"底纹在抢人像" →
**六套里四套误报**。我差点去改没问题的设计。

**修法**：改用**高频能量**（同上），或直接量"偏离纸色的像素占比"。

## 谎报 3 · 只测左右两边带

**问题**：HUD 和纵深网格的内容在**上下横带**（刻度轨、透视网格横线），
不在左右竖带 → 明明有内容却报"边缘太空"。

**修法**：四边都测。但注意下一条。

## 谎报 4 · 把"底边留白"当缺陷

**问题**：底边 13% 是**留给水印信息带**的，低细节**才对**。
我却把它算进"四边有内容"的判据 → 正确的事情被判成缺陷。

**修法**：判据改为「左右上三边有内容」，底边明确排除并在代码里注释原因。

## 谎报 5 · 拼接两条边带后 reshape

**问题**：把左右两条边带 `np.concatenate` 后 `reshape` 成一张假图再算模糊 —— 
**空间结构被破坏**，算出的高频值是假的。连续两次报出**完全相同的数字**，
这才让我起疑。

**修法**：分别在各边带上计算再平均。

> **教训**：当指标连续给出**可疑地相同**或**可疑地完美**的结果时，
> 先怀疑指标，不要先怀疑设计。

# 三、流程与判断的错误

## 错误 1 · 猜参考图的意图（浪费整轮）

用户发了 2×2 四格照片拼图，说「背景类似左下那种效果」。
我做了 5 轮分析（亮度、主色、边缘密度、面板边界、梯度拟合、FFT 周期结构、
与我自己生成过的 49 张图逐张比对）——**仍然认不出意图**。

正确的做法**一开始就做**：把测出的事实摆出来，然后**给可选项让用户确认**。
我最后是这么做的（A/B/C 三选一），用户一句「A」就解决了。

**代价对比**：5 轮分析 ≈ 大量 token 且没结论；问一次 ≈ 一句话。

**规则**：参考图读不出意图时，**先报实测事实 + 给选项**，不要连续猜。

## 错误 2 · 把用户的否定理解反了

用户说「**不是暗色风**」。我理解成"不够暗"，
于是**把整套浅色改成深色** —— 方向完全相反。
用户实际意思是「**不该是暗色**」（当时方案是深色）。

**规则**：中文否定句"不是 X"在配色语境下极易反向。
拿不准时**先确认**："您是说现在太暗，还是说不该用暗色？"

## 错误 3 · 自己发明约束

用户说"白天展会、浅色风"。我把"浅色"做成了**接近纯白**——
"背景不要纯白、可以有颜色"这一层是**我自己加的约束，用户从没要求**，
而且它和"炫酷"冲突。用户后来明确纠正："背景不一定要纯白啊"。

**规则**：约束只能来自用户或物理事实。自己的审美偏好不要写成规格。

## 错误 4 · 该做的需求做漏了

用户提醒"你忘了？"的两项：
- **`#SpacemiTDevCon` 水印**：需求原文里有，我只放在水印带、没烙进背景；
- **「SpacemiT DevCon 2026」Logo**：需求原文里有，整套方案里没有 Logo。

**规则**：需求原文在 `01-项目需求与验收.md` §1 逐字保留。
**每轮交付前对照它逐条勾一遍**，尤其是"物料清单"和"社交传播"两段——
那两段最容易被当成"配套小事"漏掉。

## 错误 5 · 该用力的时候绕过去了

需求写「**一键分享**至小红书或朋友圈」，我第一轮直接用"做不到"一句带过。
用户指出后重做，才把能做的部分（预裁比例、现成文案、唤起 App、
微信 JS-SDK 可配置）全部落地。

**规则**：需求做不到时，正确做法是**拆开逐条给结论**（能/部分能/不能），
并把"能做的部分做到极限"，而不是一句"做不到"。

# 四、抠像：一次「看着能跑」的交付（2026-09-14）★

## 坑 7 · 拿检测掩码当抠像

**现象**：成片里的人像是**从一块方形框里挖出来的** —— 下半身被框切断、边缘是折线、
没有发丝。用户看一眼就判「抠像完全失败」。

**根因**：YOLOE 输出的是「框 + 框内多边形掩码」。那份掩码是为**数人**设计的：
分辨率只有 proto 的 160×160，而且**只在框内有效**。拿它当 alpha，
等于用检测结果冒充抠像结果。

**修法**：另接一个专门做人像 matting 的模型（MODNet），逐像素出软 alpha。

**教训**：**「分割」和「抠像」是两件事**。能分出人 ≠ 能抠干净。
交付前该问的一句是：「**这条边是谁给的？**」

## 坑 8 · 想当然地「人越大越准」

**现象**：为了让人在画面里更大，我把检测框扩成竖构图裁切再喂给 MODNet。
结果**比整幅直出还差**：

| 图 | 整幅直出 | 按人框裁切 |
|---|---|---|
| 办公室抓拍（人在画面里小） | 0.00002（几乎全空） | **0.10**（有人了，救回来了） |
| 海边 3 人（人本来就大） | **0.268**（很好） | 0.020（几乎全空，还冒出一堆错位的白块） |

**根因**：MODNet 对输入裁切**极敏感**。同一张图，只把裁切起点从 y=0 挪到 y=6，
覆盖率就从 0.113 掉到 0.020。它不是「人越大越准」，而是「**越接近它训练时的取景越准**」。

**当时的修法**：主路回到**整幅直出**；只有整幅确实没找到人时，才按人框裁切**重试一次**，
且重试结果必须与检测掩码 **IoU ≥ 0.30** 才采纳。

**这个修法本身也错了（2026-09-14 当天复核）。** 上面那张「海边 0.268 → 0.020」的表，
用的是**一个没套住人的框** —— 我把 alpha 的包围盒当成了「检测框」，而那张图里
MODNet 整幅只抠出了部分人，包围盒自然歪。换成正经的人框后，六档扫描结果是这样的
（人像按「占画面高」合成到 2592×1944 展台画布，与参考 alpha 比 IoU）：

| 人占画面高 | 按人框裁切（外扩 1.25×） | 整幅直出 |
|---|---|---|
| 20% | **0.87** | 0.00 |
| 30% | **0.91** | 0.20 |
| 40% | **0.91** | 0.61 |
| 55% | **0.63** | 0.39 |
| 75% | **0.76** | 0.70 |
| 95% | 0.54 | 0.54 |

裁切**全面占优**，人越小差距越大 —— 而展台就是「人站着、镜头包一大片背景」。
**现行流程：有框就裁切（主路），裁切不行才整幅（退路），都不行退检测掩码。**

**教训**：**「非空」不等于「对了」**。覆盖率阈值只能拦住全空，
拦不住**自信的错答案** —— 需要一道独立的**一致性判据**（这里用 IoU）。
这条和「二、验收指标骗人」是同一个病：**判据本身没被验证过**。

**更狠的一条教训**：**别用一次观测去改流程顺序。** 0.268→0.020 那次是**单个样本**，
而且样本里的「框」本身就是错的 —— 我却拿它把「裁切优先」推翻成「整幅优先」，
还写进了纪律。凡是定顺序/定阈值的决定，**按一个自变量扫一遍**（这里是「人占画面多大」），
别拿一次抓拍下结论。

## 坑 9 · EP 编译失败是「硬崩」，不是「慢一点」

**现象**：把 MODNet 挂进原来那套 EP 降级阶梯（拿不到核就逐级降档），
worker 进程**直接死**：

```
terminate called after throwing an instance of 'std::runtime_error'
  what():  operator compile failed at node (BatchNormalization_197),
           The dim value of scale, bias, mean and var must be equal to input_channel
```

**根因**：EP 的降级阶梯只对「**拿不到核**」有效。而**编译期不支持的算子**
会让整个进程崩掉 —— C++ 的 `terminate` 不是 Python 异常，`try/except` 一句都拦不住。

**修法**：新模型先进管线之前，**单独起一个进程试跑一次**；试通的才接进服务，
并且用 `cpu_only=True` 明确钉死在 CPU。

**教训**：**不要把没试过的模型直接塞进服务里。** 试的成本是 1 分钟，
崩在现场的成本是整个工位停摆。

## 坑 10 · 同一条资源有几个读者，就得有几个生产者

**现象**：大屏（`/stage`）和拍摄位（`/`）同时开着，两边预览都卡成幻灯片；只开一边就正常。

**根因**：`/api/preview.mjpg` 每个连接各自 `mjpeg_stream(camera, ...)` —— 两个页面 = 两个线程读**同一个** V4L2 句柄、
各自编一份 JPEG。帧被轮流吃掉，两边都不流畅，CPU 还编了两份。

**修法**：`camera.PreviewHub`：一条线程抓帧 + 编码，N 个连接只订阅结果；新连接立刻拿到最近一帧
（不再黑屏几秒），慢连接自动丢帧。

**教训**：**动手前先问「这条资源有几个读者？」** 一台相机、一个串口、一个文件句柄，
只要读者 > 1 就要「单生产者 + 分发」。共享资源上的竞争不会报错，只会**变慢** ——
而「变慢」最容易被当成玄学。

## 坑 11 · 句柄废了，但对象还在

**现象**：预览黑屏，`/api/state` 一直报 `CameraError: 读到空帧`，重启服务立刻就好。

**根因**：相机 USB 重新枚举（dmesg：`device descriptor read/64, error -71`
→ `probe with driver uvcvideo failed with error -71` → 重新枚举），video 节点从 `video1` 变成 `video2`。
进程手里那条 fd 指的是**已删除**的旧节点 —— `ls -l /proc/<pid>/fd` 里能看到 `-> /dev/video1 (deleted)`。
`cv2` 的 `read()` 从此恒返回 False。

**修法**：连续 3 次读空帧就认定句柄废了，`Camera.recover()`：
**关掉 → 按 by-id 重新解析设备 → 重开**（带冷却，别把重连打成风暴）。

**教训**：**分清「这一刻读不到」和「这个句柄已经没救了」。** 前者重试有用，后者重试到天亮也没用。
判据是：这个错误**恒定吗**（每次都一样、等多久都不变）？

## 坑 12 · 把「够不够快」当成「稳不稳」：带宽也要做预算

**现象**：拍照（切到 2592x1944）前后相机报 `Failed to resubmit video URB (-1)`、
`Failed to set UVC probe control : -71`，随后设备掉线重新枚举。

**根因**：DICOTA 4K 挂在 **480 Mbps 的 USB2 hub** 上，USB2 高带速实际可用约 **35 MB/s**；
MJPG 2592x1944 每帧 1~2 MB，相机标称 30fps → **30~60 MB/s**，一档就顶穿。
带宽不够时的表现不是「慢」，而是 **URB 溢出 → 协议错误 → 设备重新枚举**。

**修法**：拍照降到 1920x1080（16:9，与预览同比例）；成片真正用得上的人像窗只有约 278x357，
多出来的像素本来就到不了成片。

**教训**：**带宽/功耗这类预算要按「最坏一帧 × 标称帧率」算，别按平均值算。**
另外：UVC 的采样率由**相机**决定（这块相机 MJPG 各档只列 30fps），软件降帧救不了链路 ——
软件能改的只有**分辨率**，剩下的要回到硬件（换口、换线、别挂 hub）。

## 坑 13 · `a and b` 会把值漏出去，属性就不再是布尔

**现象**：相机加了「图片源」后，`is_open`（原本 `return self._status.ok and (self._cap is not None or self.mock)`）
多了一个字符串操作数 `self.image_source`。函数照常「能用」（真值不变），
但**返回值变成了一个路径字符串**。`assert cam.is_open is True` 立刻挂 —— 而如果
这个值进了 `/api/state`，前端拿到的就是一条路径而不是 `true`。

**根因**：Python 的 `and` 返回**操作数**，不是布尔。前面全是 bool 时看不出来，
一旦某个操作数换成字符串/数字就漏了。

**修法**：属性/接口的返回值一律 `bool(...)` 包一层。

**教训**：**「能用」和「类型对」是两件事。** 边界上加测试时，
断言要写 `is True` 而不是 `if x:` —— 后者对字符串同样成立，测不出这个 bug。

## 坑 14 · 模型越大，边不一定越好

**现象**：本项目要「专门的抠像模型」，于是把手上三个都量了一遍
（本机同一张 500×375 人像，CPU）：

| 模型 | 输入 | 耗时 | 覆盖率 |
|---|---|---|---|
| **MODNet** | 256² | **298 ms** | 0.268 |
| u2net_human_seg | 320² | 1203 ms | 0.274 |
| rmbg14 | 1024² | 3059 ms | 0.272 |

出图的边在同一观感档，贵的那两个**没换来更好的边**，只换来 4~10 倍等待。

**教训**：**「更专业」要用同一张图量出来，不是从模型大小推出来。**
在 35s/人 的预算里，把 3 秒花在一个看不出区别的模型上，是拿参会者的等待换心安。

## 坑 15 · 「救场」写成静默替换，配置错了会假装正常

**现象**（2026-09-15 真机）：`BOOTH_CAMERA_DEVICE=/dev/video99`（这个节点不存在），
`Camera.open()` 却**成功**返回：`ok=True`、`detail='ok'`、`status.device` 写的是按名字
解析出来的 by-id 路径。也就是说——**你想让它用 A，它偷偷用了 B，还告诉你一切正常。**

**怎么来的**：为了治「USB 重新枚举后 video 序号漂移」（现场实测 video1 -> video2），
`open()` 里加了三级回退：显式指定 → by-id 解析 → 上次开成功过的那个。
本意是救场，写法是 `device = self.requested_device or resolve_device() ...` 再加一句
`if not os.path.exists(device): device = resolve_device() or ...`——
于是「操作员显式钉死的路径失效」和「自动解析」被合并成了同一条静默回退。
测试 T-2 的 c) 组 8 项全红（断言 `open()` 该报错、`status.device` 该是请求的那个）。

**为什么比直接失败更糟**：装置看上去一切正常，画面却是另一路。现场不会有人去查，
等到发现「配置是错的」，通常已经拍了一批。这和「虚报成功」是同一类问题，只是方向相反——
本项目的规矩是**降级可以，但必须留痕**，静默替换刚好把痕抹掉了。

**修法**：把两种来源的规矩分开。

- **显式钉死**（`BOOTH_CAMERA_DEVICE` / `Camera(device=...)`）：要么用指定的那个，要么
  `raise CameraError("指定的设备不存在：...")`，`status.device` 记的是**请求的**那个。
- **没钉死**：按 by-id / 内核设备名解析，解析不到就如实报「找不到可用相机」，
  不跑去开一个碰巧存在的别的节点。
- 重新枚举的救场交给 `recover()` **显式解绑**（`self.requested_device = None` 之后再解析），
  并把新设备写进 `last_recover_note`。重连是明说的事，就该留痕。

**教训**：**回退要写在「明确发生某件事」的那条路径上，不能写进通用取值里。**
判断标准很简单：这个值变了，读状态的人能不能看出来？看不出来就是错的。

## 坑 16 · 句柄能修，总线上没有的东西修不了

**现象**（2026-09-15 11:54 真机）：服务好端端的，相机突然没了。预检三项红：

```
[FAIL] by-id 解析  · 既没有 DICOTA 的 by-id 链接，也没有 /dev/video1
[FAIL] 能否打开  · 找不到可用相机：by-id 与内核设备名都没解析到
```

dmesg 说得很清楚：

```
uvcvideo 7-1.1:1.1: Failed to set UVC probe control : -71      ×7
usb 7-1.1: USB disconnect, device number 71
usb 7-1-port1: Cannot enable. Maybe the USB cable is bad?      ×4
usb 7-1-port1: unable to enumerate USB device
```

**试过没用的**（都别再浪费时间）：

| 动作 | 结果 |
|---|---|
| 重开设备节点（`Camera.recover`） | 节点不存在，无从谈起 |
| hub 驱动 `unbind`/`bind` | `echo: I/O error`（驱动不是 hub） |
| hub `authorized` 0 → 1 | 成功，但下游口还是 enable 不了 |
| **控制器 `unbind`/`bind`** | **相机立刻回来了**（video2 → video1，9.7s） |

**根因**：`recover()` 修的是**句柄**，前提是设备节点还在。相机从总线上掉下去之后，
`/dev/v4l/by-id` 整个目录都没了 —— 这时候内核层面那个口已经 disable 了，
只有把整条 xhci 控制器重新 bind，内核才会给口重新上电、重新枚举。

**修法**：`camera.Camera.usb_reset()` + 操作员面板按钮 + 自愈时自动升级一次。
三个细节值得记：

1. **先知道复位哪条总线**。相机不在的时候没法从节点倒推，所以开成功时就记下
   `xhci-hcd.N.auto`（`/sys/class/video4linux/videoN` 的 realpath 里那一段），
   并落一份缓存 —— 否则「知道要复位，但不知道复位谁」。
2. **判据要用两个与**。`resolve_device() is None` **且** 上次用的节点也不在了，
   才算掉线。只看前者的话，udev 还没把软链建回来的那一瞬会被误判，
   白白把整条总线（包括其它设备）复位一次。
3. **这条路径要十几秒，必须限频**。单独给 30 秒冷却，比普通重连的 6 秒长得多。

**教训**：**排障要分层分到底**：句柄 → 设备节点 → USB 端口 → 控制器，一层层往下。
每一层能修的东西不一样，修不了的时候要**说清楚是哪一层没救**，
而不是把「试了没反应」笼统报成「相机坏了」。

## 坑 17 · USB 链路上的每一次「重新协商」都是风险敞口

**现象**（2026-09-15）：连拍 12 张，第 6 张起相机掉下总线，剩下的全废（5/12）。
dmesg 的落点很明确：

```
uvcvideo 7-1.1:1.1: Failed to query (GET_CUR) UVC probe control : -71
uvcvideo 7-1.1:1.1: Failed to initialize the device (-71)
uvcvideo 7-1.1:1.0: probe with driver uvcvideo failed with error -71
usb 7-1.1: USB disconnect, device number 12
usb 7-1-port1: Cannot enable. Maybe the USB cable is bad?
```

**写代码时没注意的事**：`_open_locked()` 无条件 `self.close()` 再开 —— 哪怕
**已经是想要的分辨率**。而一次拍摄的路径是：

```
抓帧(预览 1280x720) → 切拍照 1920x1080 → 抓帧 → 切回预览 1280x720
```

中间两次 `close→open` 全是真协商。camera.py 自己的注释就写着
「close→open 换分辨率是整场里对 USB 链路最重的动作」—— 结果最重的那件事，
我们每个参会者身上做了两遍，其中一遍还是白做的。

**修法**：已经在要的尺寸上开着就直接复用。

```python
if (not self.mock and self._cap is not None and self._status.ok
        and tuple(self._size) == (int(size[0]), int(size[1]))):
    return self._status
```

**实测收益**（各连拍 12 张，真相机）：

| 拍照分辨率 | 每次拍摄的 USB 重新协商 | 成功率 | 中位耗时 | 折算吞吐 |
|---|---|---|---|---|
| 1920x1080 | 2 次 | 12/12 | 4.31 s | 836 人/小时 |
| **1280x720（与预览同尺寸）** | **0 次** | 12/12 | **2.92 s** | **1232 人/小时** |

**教训**：**「最重的动作」不能出现在每个参会者的必经路径上。**
两个推论：

1. 能复用的句柄不要关。判断条件要写清「什么时候不用重开」，而不是默认重开。
2. 分辨率切换本身就是那件重活 —— 如果成片窗口只有约 278x357 px，
   而 1280x720 已经够用，那这档切换换来的只是风险，不是画质
   （`BOOTH_PHOTO_SIZE=1280x720` 可切，见现场故障处置手册）。

## 坑 18 · 抠像的边在链路上被降采样了，成片里的边是「放大」出来的

**现象**（2026-09-15 现场）：参会者反馈「抠像效果差劲，而且进行了压缩？」。
成片人像窗里的头发是一团糊的、边缘发虚，脸上一层灰。

**量出来的**：

```
源照片        1920x1080
回传的 alpha   640x360      ← seg 请求里 mask_max_side=640
成片人像窗     279x357
```

alpha 640 → 放大 3 倍贴到窗里。**「压缩」的观感不是错觉：边确实是放大出来的。**

**两个独立的错，叠在一起：**

1. **一份参数管了两件事。** `mask_max_side` 是给「数人 / 大屏画框」用的二值掩码定的
   —— 那份 640 完全够。但同一个请求把**抠像的软 alpha**也按它缩了。掩码是给人看的框，
   alpha 是要往成片上贴的边，两者对分辨率的要求差一个量级。
   修法：协议里拆出 `matte_max_side`，默认 `0`（不缩）。
2. **垫错了一层底。** 抠像层的掩码外如果垫的是合成用的**暗底**，软 alpha 的过渡带
   会按比例把暗底混进来 —— 人周围一圈灰黑描边，脸上一层灰纱。
   被问到「抠得像不像」时，这一圈才是主因，跟模型准不准无关。
   修法：掩码外填**原片**（过渡带混出来的就是人自己的颜色），再用 alpha 加权的邻域均值
   做一次去污染（`_decontaminate`），把「人+旧背景」的混合色换成人的颜色。

**还有一个白丢的精度**：MODNet 的输入是**动态维度**（`height`/`width` 是符号维度），
早期按 `MATTE_INPUT = (256, 256)` 写死。只改输入边长，同一张图 256→512 的边差一个档，
代价 326→1340 ms。

**教训**：

- **一个数字服务两个目的时，先问「谁的需求更严」。** 这不是调参问题，是把两件事
  塞进了一个参数。
- **抠像的边有三段：模型算的、回传的、贴上去的。** 任何一段被降采样，
  前面算得再准也是白算。查「边不干净」要从这三段挨个量尺寸，别一上来就换模型。
- **模型「多大」不止是模型大小，还有输入分辨率。** 坑 14 说「别从模型大小推质量」，
  这条是它的另一半：**同一个模型换个输入尺寸，也可能比换个模型划算得多** ——
  先看它支不支持动态输入。

## 坑 19 · 取景框把宽、高各自夹进画面，人被压扁了

**现象**（2026-09-15 现场）：「我的人像被压窄了？？」

**量出来的**（同一张贴脸抓拍）：

| 量什么 | 值 |
|---|---|
| 人像包围盒 | 1189×1007（宽高比 1.181） |
| 取景框**建立**时的比例 | 0.78（竖版人像窗，正确） |
| 夹取**之后**的比例 | **1.475**（1593×1080） |
| 塞进 0.78 的画布 | 人横向只剩 **53%** |

**怎么来的**：`_frame_box()` 建框那一步是对的 —— 先扩 pad、再按目标比例重算宽高。
坏在最后「夹进画面」：

```python
bw = min(x1 - x0, float(W))     # ← 宽自己夹
bh = min(y1 - y0, float(H))     # ← 高自己夹
```

只要有一个方向装不下，比例就没了，另一个方向还留在原尺寸。而「装不下」恰恰发生在
**人最满画面的时候**（贴脸、张开手臂、横向构图）—— 也就是最显眼的时候。人越小越正常，
人一大就变形，所以它躲过了所有「人站着、镜头包一大片背景」的测试图。

**修法**：等比缩。

```python
shrink = min(1.0, W / bw, H / bh)
bw, bh = bw * shrink, bh * shrink
```

代价是横向会裁掉一部分（竖版窗口 + 宽人像本来就是这个取舍），但人不再变形。

**教训**：

- **凡是「夹到范围内」的操作，只要和形状有关，就必须等比缩。** 宽高各自 `min` 是最容易写、
  也最难发现的一种错：不报错、不越界，只在某些输入下悄悄改变形状。
- **这张图差点被我判成「正常」。** 第一次做参照图，我用的是**同一个** `_frame_box()` ——
  参照图也一起被压扁了，两张图并排一看「一致」，于是「验证通过」。
  参照物必须来自**另一条独立路径**（这里是原片直接等比裁切），否则量的是自己的 bug
  跟自己一不一样。这跟 §二「验收指标骗人」是同一个坑的另一种形态。
- 自检里钉一条比例断言：`stylize.self_test()["frame_aspect_ok"]`，用一个「又宽又满」的
  掩码复现现场那张贴脸抓拍。

## 坑 20 · 「盖住底图上的东西」盖成了另一个看得见的矩形

**现象**（2026-09-15 现场）：「为什么还是加上了一个矩形框在人像后面？」

**两个独立的问题，凑成了同一句抱怨：**

1. **该盖的没盖全。** 官方主视觉的人像窗里画着一个**浅灰人形占位**（原始素材就这样），
   我们拿一块自制暗底去盖，位置按「窗框往里缩 6px」算 —— 窗框其实只有约 4px 宽，
   于是留了一圈浅灰细缝。那条缝就是「人像后面多出来的矩形」的左边。
2. **不该盖的也盖了。** 芯片特写那套人像窗下面什么都没有，我们照样糊了一整块矩形上去。
   那块矩形是**凭空画的**，凭空画的矩形当然看得出来。

**修法**：别猜 inset，让底图自己说。

```python
luma   = ...
chroma = crop.max(2) - crop.min(2)
mask = (luma > 150) & (chroma < 60)      # 占位是中性灰且亮；窗框是品牌蓝
if mask.mean() < 0.02:                    # 没有占位 → 什么都不画
    return None
```

顺带把盖底从「径向光 + 网格」改成**一道极轻的上下渐变**：纹理会把「盖住的区域」
变成「看得见的一个物体」。现在这块底的边界就是窗框本身。

**教训**：

- **「盖住」这个动作，边界必须由被盖的东西决定，不能由我目测。** 目测出来的 inset
  只要差 2px 就是一条缝，而且素材一换版本就重新错一遍。
- **没有东西要盖的时候，不要盖。** 同一段代码要同时服务两套底图时，
  「无条件执行」= 在其中一套上凭空多画一层。做成「有则盖、无则跳过」，
  两套都自动对 —— 这跟坑 15「回退不能悄悄顶包」是同一类毛病：条件没写清，
  代码就在我没想到的那条路上自作主张。
- **纹理是「这是我加的」的信号灯。** 只要盖底上有网格/噪点/辉光，它就不再是背景，
  而是一个贴着看的方块。要让一块补丁消失，就让它平。

## 坑 21 · 人贴对了，但「窗框」把人切成了一个矩形

**现象**（2026-09-15 现场，紧接着坑 20）：「为什么还是加上了一个矩形框在人像后面？」

用户说的是「**还是**」—— 因为当时**上机的是 patch78~88**，坑 20 的修法（patch89）
只改了本地、没同步到 K3，窗口里那块暗底面板还在。一句话里其实叠着两件事：

- **A（叠加层）**：旧代码无条件往窗里糊的那块「暗底面板」，就是人像背后那块矩形。patch89 已修，同步后消失。
- **B（结构）**：人本身的轮廓被矩形取景框切出的直边。patch89 管不到，这一条才是本坑。

先按坑 20 的办法把「同步之后还加不加东西」验证一遍，再动 B：

- 逐点比对「底图」与「成片」，diff 的包围盒正好等于窗口内框 `inner`；
- 窗口**四角**的 diff 是 `0.00`（一个像素都没动）；
- 覆盖掩码 `_window_cover_mask()` 对芯片底图返回 `None`（本来就没画任何东西）。

也就是说，同步之后**没有任何东西被叠加上去**了。剩下那块「矩形」就是**人自己**。

**根因**：人像是顺着轮廓的，取景框是矩形的，两者不可能处处贴合。

- 取景框受「窗口宽高比 0.78 + 不能越出照片」双重约束。实测一张站姿抓拍：
  人的包围盒 1105×853，要装进 0.78 的框就得要 1105×1417，**比照片还高**，
  于是被等比缩到 842×1080 —— 框比人**窄** 263px。人的两肩被硬生生切掉，
  切面正好落在窗框的左、右、下三条边上。
- 于是「人的轮廓」局部等于「窗框的直边」，远看就是一个亮矩形贴在图左上角。
  因为窗框是矩形，这个 bug **只在人比窗宽的时候**才出现 —— 人坐远了就「正常」了。

**修法**：不去改取景（人就是那么宽，改不了），而是**让窗口四周淡出**：

```python
WINDOW_FEATHER = (0.10, 0.06, 0.10, 0.16)   # 左 / 上 / 右 / 下，占窗口宽或高的比例

def _window_feather(size):
    """窗口四周的柔化权重 0..1（中间恒为 1，四边淡到 0）。"""
    ...
    return (m * m * (3.0 - 2.0 * m))         # smoothstep：不带硬拐点
```

贴人之前在 alpha 上乘这一层权重。人的轮廓现在是**淡进背景**的，一条直线都不剩。
底面留得最宽（0.16）—— 人本来就是被画面下沿截断的，那里淡出去最自然。

**实测**：芯片底图窗口左缘的「内 − 外」亮度差从 **+16 降到 +0.3**
（数值上就是「没有硬边」）。自检里钉一条：`keyvisual.self_test()["feather_ok"]`。

**教训**：

- **「凭空多了个几何形状」要先证明它是加出来的。** 我一开始默认是叠加层问题，
  查了两轮叠加层（坑 20 的延续）。真正定位靠的是**四角 diff = 0** 这一条：
  叠加层一定会动到角，人的轮廓不会。**先做「是不是我加的」这个判定，再去修。**
- **反向的证据比正向的更有用。** 「四角 diff=0」没有告诉我错在哪，但它一刀砍掉了
  整条错误假设链，比再多看十张图都省时间。
- **修完必须同步、同步完必须重跑。** 这句抱怨之所以带「还是」，根因是 patch89 只落在
  本地工作区。**没有部署的修复等于没修**；而且用户看到的现象会把两条独立的 bug
  混成一句话 —— 排障第一步永远是确认「他现在看的到底是哪一版」。
- **矩形取景框 + 顺着轮廓的人 = 必然有切面。** 这不是参数没调好，是**结构**上就有的。
  凡是要把不规则的形状放进规则的框里，都要问一句：**切面露在哪儿？**
  切面可以藏在画面外、藏在背景色里、或者用渐变抹掉 —— 但不能假装它不存在。
- 排这条 bug 时我用洋红底做「抠像干净吗」的对照图，**结果被自己的对照图骗了**：
  低 alpha（0.1）的雾混在饱和洋红上几乎看不出来，混在暗底（亮度 30）上却很明显。
  **对照图的底色要跟真实底色同量级**，否则等于用一个看不见的指标做验收（坑 8 的变体）。

## 坑 22 · 成片比例和出图对不上时，「裁哪儿」不是随便挑的

**现象**（2026-09-15）：换上一张新的主视觉（一张成片底图）后，
「人像贴进窗里」这套几何全部失效 —— 窗口越界、人压标题、比例不对。

**根因**：新出图是 **1264×848（1.49:1）**，成片是 **16:9（1.78:1）**，
差 19%，不可能直接铺。而这张图的构图把可用空间**从三面锁死了**：

| 区域 | 内容 | 能不能裁 |
|---|---|---|
| 左上（y < 0.42） | SpacemiT / DevCon 2026 标题字 | ❌ 字会被切 |
| 右侧（x > 0.45） | 芯片主体 | ❌ 主体会被切 |
| 底部 | 连续暗场 | ✅ 唯一的余量 |

**修法**：把「裁」这件事**从运行期搬出来，离线烤成 1600×900 再进仓库**
（`tools/make_keyvisual.py` 的 `bake()`：按宽度铺满 → 顶部对齐 → 从下往上裁）。
好处是运行期不再需要对齐参数，窗口的归一化坐标可以直接按成片尺寸量。

**配套的坑**：窗口比例**必须**等于 `PORTRAIT_SIZE` 的 0.78。
`_compose_cutout()` 是把抠好的人直接 `resize` 到窗口尺寸的，
窗口比例差一点，人就被横向或纵向拉变形（坑 19 的邻居）。
所以窗口是**扫出来**的，不是目测框的：在左栏里搜「边缘能量 + 亮度标准差」
最低、面积又不至于太小的 0.78 框。

**两个数要同时看**：干净度（越低越好）**和**面积（太小人会被缩没）。
只按干净度选会选到一条缝；只按面积选会选到压着标题的框。

当前实测：`box = (0.0300, 0.4360, 0.2580, 0.9550)` → **365×467px**（比例 0.7800），
边缘能量 0.054 / 亮度 std 2.20；标题最低一行在 y=386（0.429），
窗口顶在 y=392（0.436），间隙 **6px**。自检：`keyvisual.self_test()` 的
`window_in_canvas` + `feather_ok`。

**教训**：

- **「比例对不上」是必须当场处理的问题，不是能拖的。** 拖到运行期
  就是每出一张图都要重算一次几何，而且缩放/裁切的参数会散进多个文件，
  改一处漏一处。「前置知识库里有现成的底图 demo」也是同一件事：
  参考图能看，但**能不能直接当素材要量过再说**。
- **素材的坐标系和成片的坐标系要尽早统一。** 烤成同尺寸之后，
  「窗口在哪」这种数字才能互相校对（标题最低一行 y=0.429 vs
  窗口顶 y=0.436 —— 这种精度只有统一坐标系之后才谈得上）。
- **素材只剩一套不等于流程坏了。** 前端那一行按钮会自动收起来
  （只有一个选项的选择器是干扰）—— 别去把它「修」成两套。

## 坑 23 · 名字改了，写死的那份没跟着改 —— 而且它不报错

**现象**（2026-09-15，底图从两套收敛成一套 `main` 之后）：
改完代码、跑完测试、真机也能出图，一切看着正常。但查 `/api/state` 时看到：

```json
"backgrounds":        [{"name": "main", "present": true, "default": true}],
"default_background": "official"        ← 不存在的名字
```

**根因**：`booth_server.py` 里把默认底图名**写死**成一个字符串常量
（`BACKGROUND_DEFAULT = "official"`），而底图的名字定义在
`render/keyvisual.py` 的 `KEYVISUALS` 里。改名时只改了后者，前者无人知晓。

**为什么没报错**：`kv.resolve()` 的契约是「认不出来就回退默认」——
这是为了不让一个手滑的字符串让参会者拿不到照片（很对）。
代价就是：错的名字也会「正常出图」，日志里一行异常都没有。
当时只有一套底图，所以回退也回到了对的一套，**现象完全不可见**。

**修法**：默认名**以注册表为唯一来源**。

```python
@staticmethod
def _default_background() -> str:
    """命名权归 render/keyvisual.py：底图换一套，这里自动跟着变。"""
    try:
        import importlib
        return importlib.import_module("render.keyvisual").DEFAULT_KEYVISUAL
    except Exception as exc:
        log("默认底图名读取失败，退回常量 %s：%s" % (BACKGROUND_DEFAULT, exc))
        return BACKGROUND_DEFAULT
```

常量降级成「注册表读不到时的兜底」，并且**下次改名不需要动它**。

**教训**：

- **同一个事实有两份声明，就会分岔。** 「默认底图是哪套」只能有一个定义点，
  别的地方只能引用它（同坑 10「一条资源有几个读者，就得有几个生产者」）。
- **「回退得很好」会把错误埋起来。** 这次不是回退写错了，而是**回退太宽容**：
  它让一个名字对不上的后端字段变得「无痛」。凡是有回退的地方，
  回退那一刻**必须留下读得到的记录**（`degraded_reason` / 日志），
  否则等于没有回退，只是把错误换了个地方躲。
- **测试不会发现它，因为它不是「坏了」而是「不一致」。** 全套回归
  （49 预检 + 29 抠像 + 20 worker + 43 控制面 + 20 e2e）全绿。它是**看状态输出
  看出来的** —— 所以改完「名字/路径/默认值」这类东西，**要去读一遍真实的
  运行时输出**，不能只看测试结果。

## 坑 24 · 「复位」写成了无条件 unbind，而真正需要的是 bind

**现象**（2026-09-15）：相机整个从总线上掉下去，操作员点「USB 总线复位」，报：

```
{"ok": false, "detail": "unbind xhci-hcd.15.auto 失败：OSError: [Errno 19] No such device"}
```

但同一个控制器手工 `echo xhci-hcd.15.auto > .../xhci-hcd/bind` 一下，
相机立即回来。也就是说：**能救，但工具自己把救法堵住了。**

**根因**：内核把整条总线注销时，**同时把驱动也解绑了**。
而 `usb_reset_host()` 的写法是「无条件先 unbind，再 bind」：对一个**已经解绑**的设备
发 unbind，内核只能回 ENODEV，于是在第一步就 return 了，`bind` 那行根本没执行。

**为什么一直没发现**：平时掉线是「设备掉、总线还在」，这时驱动还绑着，
unbind+bind 完全正常。只有「整条总线被注销」这种比较少见的情况会踩到。

**修法**：把「走哪条路」提出来单独判断，并且可测。

```python
def usb_reset_plan(host, driver_dir=USB_DRIVER_DIR, device_dir=None) -> str:
    # 返回 "cycle" / "rebind" / "gone"
    • cycle  —— 驱动还绑着：unbind 再 bind
    • rebind —— 驱动已被内核解绑：直接 bind
    • gone   —— sysfs 里连设备都没了：诚实说「请人工插拔」
```

判据是两个目录：**驱动目录里有没有这个名字**（绑没绑）、
**平台总线上还找不找得到这个设备**（还在不在）。两个都是纯状态，
所以能拿假目录测（`tests/test_camera_heal.py` 的 E 段，7 项）。

**教训**：

- **「复位/重启」这类动作要先读状态，不能写成固定的两步。** 写成 `unbind; bind`
  就假设了「一定是绑着的」；一旦实际状态不是，第一步就报错并中断，
  **后面的步骤连执行都不会执行** —— 失败信息还指向错的方向。
- **“没用过的那条分支”要主动去踩。** 这个坑不是写错了代码，是**一条真实存在的分支
  从来没有人验过**。现场自愈路径尤其如此 —— 它只在出事的时候才跑，
  而出事的时候就是最不能现场改代码的时候。
- **失败信息里要带上「下一步该干什么」。** 现在 `gone` 这条会明说
  「请人工重新插拔相机」，而不是把 errno 丢给操作员自己猜。

## 坑 25 · 把功能删了，判据还钉在旧窗口上

**现象**（2026-09-15）：现场判定「风格只留原色」，四档强风格化从 `render/stylize.py`
里删掉。删完跑自检，`card.self_test()["ok"]` 变成 `false` —— 可成片本身没问题。

**根因**：自检里钉的是

    全图平均亮度 15~35   且   像素值>200 的占比 1%~6%

这是给**四档**定的窗口（那四档本来就该把整块板子压到均值 25 上下）。而**原色刻意
不进这个窗口** —— 原色的脸要留在暗底上，把脸压到 30 就成了剪影。
于是「删掉一个功能」把「一直拿一个假判据给这个功能打分」这件事暴露了出来。

**这不是第一回。** 坑 23 是「改名后写死的那份没跟着变」，这一条是同一个病的另一面：
**判据也是「同一事实的第二份声明」。** 清单、默认值、阈值、判据 —— 只要抄成两份，
删/改一份时另一份不会报错，只会给出一个错的结论（要么假红，要么假绿）。

**修法**：

1. 原色的判据只定义**一次**：`natural_metrics_ok()`，窗口提成常量
   `NATURAL_MEAN_RANGE` / `NATURAL_HI_MAX`；`card.self_test()`、
   `tools/make_samples._check()`、样张汇总页**打印**的那行判据，全从它引。
2. 不把断言删掉了事：自检里留一条暗调基准 `dark_ref_mean`（同一张图走一遍当年的
   暗调校准，实测 ≈29.7），和原色均值摆在一起 —— 用它证明原色确实**没**被压暗，
   比一句「应该够亮」有信息量。
3. **删一个枚举值 = 删它所有的字符串，接着扫一遍调用方。** 这一轮扫出两种下场：

   | 写法 | 下场 | 危害 |
   |---|---|---|
   | `card.compose(style="mono")`（`tools/make_samples.py` 2 处） | **直接抛 `ValueError`** | 幸好是响的 |
   | `POST /api/capture {"style": "mono"}`（`tests/` 6 处） | 服务端**静默回落到原色** | 断言照样通过 → **假绿** |

**教训**：

- **报错的还算好，静默回退的才是真危险。** 回退是留给现场的后路，不该变成
  留给自己的免责声明：测试里点了一个已下线的值，拿到的是原色，断言还在 —— 绿灯。
- **判据落在哪个对象上，要说清楚。**「暗调窗口」量的是**暗底上的人像板**，
  不是**贴在亮底板上的证件照**。同一个函数被两种对象用，判据就必须分家。

## 坑 26 · 换一张底图，两处「猜」同时翻车

**现象**（2026-09-15）：现场要求「换成这两张，随机使用」—— 暗调那张之外，加一张
**亮调**（白台面）的同版主视觉。底图本身换上去没问题，但立刻冒出两个新毛病：

1. 亮底那张的成片，人像窗里**糊了一块深色矩形**（暗底那张完全看不出来）；
2. 暗底那张调暗人的那套参数，套到亮底上之后，**人比整个画面暗一档**。

**根因 1：启发式没有「这是哪张图」这个前提。**

`_window_cover_mask()` 原来是纯启发式 ——「窗内中性灰且亮的像素就盖掉」（当年为了
盖素材自带的浅灰人形占位，见坑 20）。暗底素材窗内是纯暗场，判定为空，永远不会盖。
**亮底素材整块都「中性灰且亮」**，于是判定为「全是占位」，往窗里糊了一整块深色。

- 同一个函数，在暗底上是「什么都不做」，在亮底上是「糊一块黑方块」——
  **判据没变，输入变了，行为就反了。**
- 它还不报错。要不是亮底和暗底反差足够大，肉眼根本看不出来（暗底上它会「恰好」正确）。

**根因 2：一个参数被两种对象共用。**

「入景暗调」（曝光 ×0.88）是为**低照度冷调底**做的：把办公室顶灯下的人往暗场里拉。
亮底是白台面平打光 —— 同一个动作下去，人就成了画面上唯一一个被压暗的东西。

**修法**：

1. **把「猜」变成「声明」。** `KEYVISUALS` 每套加一句 `placeholder: True/False`，
   `_window_cover_mask()` 先看这句；声明没有就直接返回 `None`，启发式只在声明
   「有占位」时用来定位占位在哪。**能不能猜对**变成了**有没有人写过**。
2. **调子跟着底图走。** 每套加一句 `tone: "dark" / "none"`，`_tone_spec()` 按它取；
   `none` 的那套 `_into_scene()` **原样返回**。
3. **两条都进自检**：`tone_quiet_untouched` —— 声明「不压暗」的底图，人像必须
   **逐像素**不变（不是「看起来差不多」）。

**教训**：

- **启发式要写清它成立的前提。** 「中性灰且亮 = 占位」这个前提是「底图是暗的」。
  前提没写下来，换一张图就变成错的 —— 而且**错得安静**。
- **凡是「因为 A 所以这么做」的参数，A 变了参数就得重算。** 底图换了一套光，
  人的调子、盖底策略、甚至连窗的位置都要重新量一遍，不能只换文件名。
- **同一段代码服务两种对象时，先把「我是谁」传进去。** 加一个声明字段，
  比调启发式的阈值可靠得多（调阈值永远是「这次对了」）。

## 坑 27 · 「框里其实没人」也能拼出一张空白照片

**现象**（2026-09-15）：真机连拍校验里 `SM-2026-0078` / `0079` 两张成片**只有底板**
（人像窗里什么都没有），但接口一路全绿：检出 1 人、`degraded=false`、每一步 step 都 ok。
出事的恰好是「镜头前只有桌面」的测试片 —— 推到现场，就是**参会者扫码拿到一张只有品牌
背景板的照片，而系统认为一切正常**。

**根因：三段各自都「成功」了。**

| 环节 | 它认为自己做了什么 | 实际上 |
|---|---|---|
| 检测 | 检出 1 个人 | 贴着画面下沿的一块误检碎块 |
| 抠像 | 返回了一张有内容的 alpha（覆盖率 0.039 / 0.056） | 内容全在**取景框之外** |
| 合成 | 把 alpha 贴进窗里，没抛异常 | `_frame_box` 按包围盒中心取景 → 框内 alpha 全是 0 → `(soft-0.06)/0.88` 之后整幅归零 → **贴上去等于没贴** |

三段之间的**契约**是「这是这个人的 alpha」，但没有一段检查过**这一帧里到底还有没有人**。

**修法**：`render_cutout()` 末尾加一道闸门 —— alpha 覆盖率低于
`CUTOUT_MIN_COVER = 0.02` 就返回 `None`，与「一个人都没检出」走**同一条**退路
（整幅兜底：人是糊上去的，但成片里确实有人）。并在 `_render()` 里留痕：拿到的 `cutout`
是 `None` 而 `alpha` 不是 `None` 时，render 步骤的 detail 追加「 · 整幅兜底」并
`log()` 一行 —— 出片能当场对账。

**阈值是量出来的**：真机有人那几张（同一窗口、五个样本）alpha 覆盖率 0.30~0.49，
误检碎块是 0.0000 —— 中间空了两个数量级，取 0.02 是很宽的闸门。

**教训**：

- **「接口说成功」不等于「成片里有东西」。** 检测、抠像、合成各自的返回值都是"正常"的，
  错的是它们**共同指向的那张图**。自检要量**成片里的内容**，不是量调用有没有抛异常。
- **每一段只保证自己那一段，就没人保证整张图。** 交接点上必须有一句
  「这个数在目标画布上意味着什么」—— 这里是「alpha 覆盖率 0.039」对「框里的覆盖率 0」。
- **兜底路要能看见。** 闸门拦住之后如果什么都不说，就变成另一种静默替换（坑 15）。
- 顺带记一条**边界**：`person_count=0`（根本没检出人）时走的是另一条路（直接整幅兜底），
  **不记**这句 note —— 这段文案只表示「有 matte，但 matte 是空的」。

## 坑 28 · 校验器用了「宽容的解析器」，坏地址一路存到现场

**现象**（2026-09-16）：给操作员面板加了个「公网取图地址」的输入框，配了校验 ——
只接受 `http/https`、不许带路径、不许带 query。本地单测过得好好的。
然后拿真机上的接口试了一条随便敲的字符串：

```
POST /api/operator/config {"public_base": "hello world"}
→ 200 {"public_base": "http://hello world", "source": "panel", ...}
```

**存下来了。** 而且二维码会照它生成、现场会照它发出去、扫开打不开。
**全程不报错，面板上还显示"HTTPS 已配置"。**

**根因**：`urlparse` 对主机名极其宽容 —— `urlparse("http://hello world").netloc`
就是 `"hello world"`。我那句 `if not parsed.netloc: raise` 形同虚设：
它只检查"有没有"，不检查"是不是"。**我拿一个"能不能解析"的判据，
去回答"这地址能不能打开"。**

**修法**：自己写一个 host 字符集的正则（字母数字点短横线 + 可选端口），
再卡端口范围（注意 `parsed.port` 对超范围会**直接抛**，得接住）。

**顺带发现的第二层**：改完代码、同步到 K3，**接口还是返回 200** ——
因为跑着的进程里是旧代码。`sync` 只改磁盘，不改内存。
重跑服务之后才生效。**"我改了"和"它在跑"是两件事**（和坑 23 同一族）。

**教训**：

- **解析器宽容，校验器就得严。** 标准库的 URL 解析器是"尽量给你解析出点什么"，
  不是"帮你判断这地址合不合法"。拿它当校验器用，等于没校验。
- **校验要拿真输入试，不能只试我想到的输入。** 我本地写的是
  `https://a.b.com/path`、`ftp://a.b.com` 这种"正经的坏输入"，
  全被拦住了；随手敲的 `hello world` 反而溜过去了。
  —— **"看着像地址"和"是地址"之间的那条缝，才是最危险的输入。**
- **这类错的代价不对称**：当时拦住只是弹一条提示；没拦住就是现场几百个二维码
  全都扫不开，而且没人知道该去查哪里。

## 坑 29 · 连号的东西当了入口 —— 公网上「从 0001 数到 9999」就是下载器

**现象**（2026-09-16）：取图页从第一天起就是 `/p/<编号>`（`SM-2026-0001`…），
`/api/photo/<编号>.jpg`、`/api/thumb/`、`/api/qr/`、`/api/photo-meta/`、
`DELETE /api/photo/<编号>` 全都拿编号当入口。局域网里没问题 —— 编号本来就是
我们自己写进二维码、发到参会者手机上的。但 A 方案要把它挂到公网域名上：
**只要有人从 0001 数到 9999，全场每一个人的照片都能被拉走，也能被删掉。**
而且这比"猜密码"容易得多 —— 编号是**连号**的，不是随机的。

**根因**：我把「主键」当成了「凭证」。编号是给人看的、可读的、可枚举的；
凭证必须猜不出来。**同一串字符承担了两个互相矛盾的角色**，而
"能取图"和"能删图"又都挂在同一个字符串上。
再往下看一层：`/p/<编号>` 既是"页面地址"又是"访问授权"，而**地址栏里的东西
会进浏览器历史、会被转发、会被截图、会被念给旁边的人听** —— 它天生就是公开的。

**修法**：

- `Record.token`：`secrets.token_urlsafe(16)` → 22 位、128 位随机。
- 路由一律走 `store.by_token()`（比较用 `hmac.compare_digest`）：
  `/api/photo/<令牌>.jpg`、`/api/thumb/<令牌>.jpg`、`/api/qr/<令牌>.png`、
  `/api/photo-meta/<令牌>.json`、`DELETE /api/photo/<令牌>`。
- 取图页只拿到令牌，**编号是从 `/api/photo-meta/<令牌>.json` 问回来的**，
  只用来显示和当下载文件名。
- 二维码缓存文件名也换成令牌（原来是 `data/qr/<编号>.png`）。
- **老记录没有 token 字段 → 空串 → 一律查不到。** 失败方向是"打不开"，
  不是"泄漏" —— 这个方向是刻意选的。

**连带的三处**（改一处不够，凡是"拿编号拼 URL"的地方都得跟着改）：

1. 前端三份：`booth.js`（成片 / 二维码 / 下载）、`operator.js`（取图页链接 /
   删除 / 二维码）、`pick.js`（URL 里那一截现在是令牌，编号另问）；
2. **二维码缓存** —— 不清就是接着发旧码，而且不报错（坑 25 的同一个病）；
3. **测试** —— 不然"编号取不到图"这条新契约没人守，哪天退回去也没人知道。

**教训**：

- **可枚举的 ID 不能当凭证。** 入口只要连号，"公开一半"就等于"公开全部"。
- **失败方向要选。** 无效令牌一律"打不开"，绝不"回退用编号" ——
  回退会把一个小 bug 变成一个泄漏。
- **改凭证 = 改一串消费方。** 服务端改完只是第一步；前端、缓存、测试、文档
  全是「同一个事实」的副本（坑 23 一族）。

## 坑 30 · 那张「手机截图」，其实不是按手机宽度排的版

**现象**（2026-09-16）：一直用 `tools/shoot_ui.py` 截「手机尺寸」的图
（`--window-size=390,844`）做破版复核。这次改取图页，顺手量了截图里内容的
右边界：**内容一直顶到 389，右边被切掉了**。看起来就是"页面在手机上横向溢出"。

**根因**：不是页面的事。在同一台机器上实测：

```
chromium --headless=new --window-size=390,300 ... → 页面里 window.innerWidth = 518
```

**Chromium 的窗口有最小宽度**（这台机器上实测 518），`--window-size` 比它小
会被夹住；而 `--screenshot` 仍然按要求的 390 去裁图。
于是拿到的是"**按 518 px 排好版、只截了前 390 px**"的图。

**教训**：

- **「我截到的图」不等于「我要求的视口」。** 破版复核的结论要建立在
  **实际视口宽度**上，不是命令行参数上。要真手机宽度，得走 CDP 的
  `Emulation.setDeviceMetricsOverride`，`--window-size` 不够。
- **差点按这张图去改 `pick.css`** —— 差一点就给一个不存在的 bug 打补丁。
  和坑 19 的"参照物"同一族：**先确认量的是不是那个东西，再动手。**

## 坑 31 · `systemctl enable --now` 不会重新读配置，而它报的是「成功」

**现象**（2026-09-16）：重跑 `server-install.sh` 改了 `frps.toml`（加了
`proxyBindAddr`），脚本打印 `active`、流程全绿 —— 但新配置**静默没生效**。

**根因**：frps 已经在跑的时候，`systemctl enable --now frps` 只做"确保它在跑"，
**不会重启**，也就不会重新读 `/etc/frp/frps.toml`。而脚本拿 `is-active` 当验收，
它当然是 active。

**教训**：

- 首装和重跑统一用 `systemctl restart`（对没跑的服务也能起来），别用 `--now`。
- **验收要看结果，不要看状态**：这里改成重启后打印 `ss -ltn | grep 10111`
  的真实绑定地址，绑到 `*:10111` 或压根没监听都会当场说出来。
- 和坑 23 同族：**改了东西 + 没人重新加载 = 看起来成了**。

## 坑 32 · 位置参数被选项吃掉，而且一声不吭

**现象**：`server-install.sh --external-ip=1.2.3.4 域名` —— 域名变成了
`--external-ip=1.2.3.4`。接下来 `customDomains` 写成这个串，打印给 K3 的
那行命令也是错的，全程不报错。

**根因**：`DOMAIN="${1:-}"`，没有区分"选项"和"位置参数"。

**教训**：脚本同时接受选项和位置参数时，必须**遍历 `$@` 分类**
（`-*` 进选项，否则填第一个空的位置槽），并且**不认识的参数要出声**。
"文档里的顺序是对的"不等于脚本健壮 —— 用户不会永远照顺序写。改完实测：

```
devcon.example.com                        -> DOMAIN=[devcon.example.com]
devcon.example.com --external-ip=1.2.3.4  -> DOMAIN=[devcon.example.com]  IP=[1.2.3.4]
--external-ip=1.2.3.4 devcon.example.com  -> DOMAIN=[devcon.example.com]  IP=[1.2.3.4]
```

## 坑 33 · `set -e` 把"尽力而为"的段落变成了"致命"

**现象**：一台机器上没有 iptables。脚本停在第 5 节（防火墙），第 6 节（启动服务）
**永远没跑** —— 隧道没起来，而前面所有输出看着都正常。

**根因**：`set -euo pipefail` 下，else 分支里的 `iptables -I ...` 失败
会直接终止整个脚本。

**教训**：给每一步标"失败到底要不要紧"：

- **非核心步骤**（防火墙、日志、开机自启）每条都 `|| warn`；
- **真正致命的**（缺离线包、解压失败、服务起不来）才 `|| die`。

判据就一句：**少了它，这套东西还能不能干活**。防火墙不该挡着"把服务起起来"。
（实测：把这几段抽出来、在没有 iptables 的机器上跑 —— 现在是打印警告后继续。）

## 坑 34 · 判「文件存在」用 `-f`，空文件被当成有效凭证

**现象**：`/etc/frp/.token` 存在但是空的（上次写到一半崩了、或被人 `touch` 出来）
→ 脚本"复用"它 → 静默写出 `auth.token = ""`，K3 拿着空密钥去连。

**根因**：`[ -f ... ]` 只回答"有没有这个文件"，不回答"里面有没有东西"。

**教训**：

- 读密钥/凭证一律用 **`-s`（非空）**，读到之后再校验一次内容；
- 写完**当场断言产物**：`grep -Eq '^auth\.token = ".+"' /etc/frp/frps.toml`
  不通过就直接 die —— 别等 K3 那边连不上再回头找。

和坑 15「救场写成静默替换」同族：**空值最危险的地方，是它一路都不报错。**

## 坑 35 · TOML 表头之后的键会归到那张表（frpc.toml 的 log 段）

**现象**：frpc 装完一直重启，日志里只有一句：

```
decode proxy at index 0: unmarshal ProxyConfig error: json: unknown field "log"
```

**根因**：`templates/frpc.toml` 里 `log.to / log.level / log.maxDays` 写在了 `[[proxies]]` **之后**。
TOML 规则：一旦出现表头，后面的键就全属于那张表 —— 于是 log 被当成了隧道字段。

**教训**：

- 顶层键一律写在**所有表头之前**（`serverAddr`、`auth.token`、`log.*`，然后才是 `[[proxies]]`）；
- 改完**当场自检**：`frpc verify -c /etc/frp/frpc.toml`（frps 同理，已加进两个安装脚本）。

这个坑的可怕之处在于：**配置文件看着完全正常**，脚本也不报错（写法本身合法），只有真跑起来才能看见。

## 坑 36 · `systemctl is-active X | sed ...` 在 set -e + pipefail 下把脚本带崩

**现象**：k3-install.sh 打印完 `frpc: activating` 就直接退出，退出码 3；
后面的“验证隧道”、掉线排查提示、末尾的操作提示全都没跑 ——
恰恰是最需要看提示的时候。

**根因**：`systemctl is-active` 在 `activating` / `failed` 时返回非 0，
写成管道就会在 `set -e` + `pipefail` 下终止整个脚本。

**教训**：状态一律先取值再判断：

```bash
STATE="$(systemctl is-active X 2>/dev/null || true)"
echo "    X: $STATE"
```

`server-install.sh` 里有一份同样的写法，已一并改掉。
同族：坑 33 —— 都是「一行看着没错的管道，把容错路径变成了致命路径」。

## 坑 37 · 隧道能登录、代理却起不来：服务端没配 vhost 端口

**现象**：frpc 日志里这两行紧挨着，很容易只看到前一行就以为好了：

```
[I] login to server success, get run id [xxxx]
[W] [devcon-booth] start error: type [http] not supported when vhost http port is not set
```

**根因**：服务器上那个 frps 的配置里**没有 `vhostHTTPPort`**（只有 `bindPort` + `auth.token`），
http 类型的隧道就没地方挂。登录成功只证明密钥对、不证明代理能建。

**教训**：

- 排查隧道一定要看到 **`proxy added` 之后没有 error**，“登录成功”不是终点；
- 服务端完整配置要有三件：`bindPort`、`vhostHTTPPort`（再加 `proxyBindAddr = "127.0.0.1"` 只绑本机）；
- 这也是为什么“反代 502”不能当成隧道在跑的证据 —— nginx 连不上 10111 和 frps 没有客户端，都是 502。

**文不对路时的退化方案（已采用）**：frpc 侧改成 `type = "tcp"` + `remotePort = 10111`，
不靠 Host 路由，把服务器的 127.0.0.1:10111 直转本机 8090。
k3-install.sh 已加 `--tcp=10111`，模板在 `templates/frpc-tcp.toml`。

**怎么确认「只绑本机」（可复用的探针手法）**：
先用 frpc 挂一条 **没用的 remotePort**（比如 10199），tcp 类型、**上游指向本机一个空端口**，
然后从公网去连那个端口：
连不上（refused / 超时）= frps 把 remotePort 只绑到了本机，可以放心用 tcp 模式；
能连上 = 等于把拍摄服务挂到了公网，绝对不能这么用。
因为上游是空端口，即使真被暴露也拿不到任何东西 —— 探针本身不带风险。

同时记一笔：同一台服务器上**可能跑着两个 frps**（7000 一个、
7001 一个），密钥不同。“密钥不对”的报错不一定是密钥错，也可能是**连错端口**。

## 坑 38 · 改了 URL 的语义，但现场屏幕上那份页面还是老的（2026-09-16）★

**现象**：拍摄位上「编号 SM-2026-0001 / 推理耗时 240 ms / 端到端 5.99 s / 检出人像 1 人」
全都正常显示，只有**成片图和二维码是裂的**（浏览器显示 alt 文本）。
取图页则是「能打开、但图出不来」。服务器侧怎么测都是 200。

**根因**：取图入口按合规要求从**编号**改成了**令牌**（坑 29）。
但现场那块屏上的页面是**改之前就打开了的**，跑的是内存里那份老 JS，
还在拼 `/api/photo/SM-2026-0001.jpg` —— 而服务端对编号一律 404（这是刻意的）。

关键在于**它不会报错**：编号、耗时、人像数是 JSON 拿的，照常渲染；
只有两张图的 URL 是前端自己拼的，于是只有它们 404。
看上去像「相机坏了 / 图片格式不对」，实际是「页面版本旧了」。

**怎么量出来的（不是猜的）**：

```bash
# 1) 当时代码是这么拼 URL 的（旧 build 备份里翻出来的）
grep -n 'api/photo' /opt/devcon/app.bak-20260915-093904/static/js/booth.js
#   242:  el.shot.src = "/api/photo/" + id + ".jpg?v=" + Date.now();   ← id 是编号
#   新版本："/api/photo/" + token + ".jpg"

# 2) 编号当入口确实 404，令牌当入口确实 200
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8090/api/photo/SM-2026-0001.jpg   # 404
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8090/api/photo/<令牌>.jpg          # 200

# 3) 浏览器里读活页面的 DOM，直接看它拼的是哪个 URL —— 决定性证据
#    操作员面板「最近成片」那几条链接是 /p/SM-2026-0006（编号），
#    而新代码是 open.href = "/p/" + item.token    → 这个标签页在跑老 JS
```

**最省事的确认手法**：让页面自己把「它以为的地址」吐出来。
服务端提供的 URL（`/api/state` 里 `recent[].thumb`）永远是对的，
前端自己拼的 URL 才会错 —— 所以「服务端字段好的、拼接出来的坏了」= 前端旧了。

**修法（让这种失败自己暴露、自己恢复）**：

- 服务端把页面版本（语义版本 + `static/` 的文件指纹）注入 HTML 的 `__BUILD__`，
  顺手给每个 `/static/...` 挂上 `?v=<版本>`：刷新一次必拿到配套的 CSS/JS；
- `net.js` 每 20 秒对一次 `/api/build`，对不上就自己刷新；
  拍摄中先不刷（`buildGuard.hold(true)`），成片卡关掉再放行 ——
  参会者正对着镜头站着的时候不能把页面刷掉；
- 成片图 / 二维码 `error` 时**说出来**（顶部黄条 + 点一下刷新），
  而不是只留一行 alt 文本让人对着裂图猜；
- 手机取图页用 `<meta name="build-guard" content="manual">` 关掉自动刷新 ——
  扫码的人可能正停在系统分享面板上。

**教训**：

- **改了接口语义，就要假设「线上有跑着老版本的客户端」，而且它们不会自己消失。**
  前端一直不刷新是常态，不是意外；kiosk 一开一整天更是如此。
- 加了新入口（令牌）**不等于**老入口（编号）会报错 —— 它只是 404，
  而 404 在页面上表现为一张裂图，跟网络、相机、编码全都没关系。
- 判断「谁旧了」的通用办法：**看错的那些 URL 是谁拼的**。
  服务端给的字段是对的、只有前端拼错的，就是前端旧了。
- 一次人工刷新只是止血；要在**没人操作**的场景里活下来，页面必须能自己发现过期。

**残留（得人工做一次）**：这个自愈只能救「改完之后加载」的页面。
当时已经开着的那几个标签页（操作员面板、拍摄位、大屏）内存里还是老 JS，
**必须手动刷新一次**才进得来自愈逻辑。

## 坑 39 · 悬空 by-id 链接让相机的自愈永远不触发（2026-09-17）★

**现象**：大屏取景框冻在最后一帧不动，拍摄位跟着卡，一卡就是**一分多钟到永久**，
一直卡到人去操作页点一次「USB 复位」才回来。用户的原话是「相机老是断流卡住」。

**先排除掉的（都有实测）**：硬件链路是好的。停掉服务做对照 ——
空闲 60 秒 0 掉线；720p MJPG 推流 30 秒 0 掉线（30.00 fps）；1080p 30 秒 0 掉线；
重启服务后连续 4 分钟预览（12fps、2 个客户端）`seq` 从 956 单调涨到 3818，
`reopens=0 / usb_resets=0 / last_error=null`。不是线、不是供电、不是带宽。

**根因（两层，叠在一起才致命）**：

1. **`resolve_device()` 把「悬空符号链接」当成了「相机还在」。**
   相机掉线后 udev 留下的 `/dev/v4l/by-id/usb-...DICOTA...-video-index0`
   会先变成**悬空链接**（链接还在、目标 `/dev/videoN` 已经没了），而 `glob`
   照样匹配得到它。原来那句 `if matches: return matches[0]` 直接把它返回了。
   于是 `recover()` 里「相机不在总线上」的判据
   （`resolve_device() is None and not os.path.exists(self._device)`）**永远不成立** ——
   应用认定相机还在，只在原地反复 `open()` 一个死节点。
2. **`recover()` 在「设备没了、又不知道控制器是哪条」时直接 `return False`**，
   连一次普通重开都不试。两条路一起堵死：不换句柄、也不复位总线。

**决定性证据（服务日志里的指纹）**：

```
09:48:40 WARN cap_v4l.cpp: requestBuffers(VIDIOC_REQBUFS): errno=19 (No such device)
09:49:10 ... 09:49:16 ... 09:49:22 ... 09:49:28 ... 09:49:34 ... 09:49:40 ... 09:49:53
```

**每 6 秒一条、连刷 73 秒** —— 6 秒正是 `RECOVER_COOLDOWN_S`，说明它在一遍遍跑
`recover()`（也就是一遍遍 `open()` 死节点），而**一次总线复位都没发**。
同期内核侧 `attempt power cycle`、`device descriptor read/64, error -71` 都有，
证明相机确实掉下总线了 —— 应用却完全没往复位那条路上走。

**修法**：

- `node_exists(path)`：解析 by-id 时必须**顺着链接看一眼目标在不在**
  （`os.path.exists` 对悬空链接就是 False）。匹配到但目标不存在 = 相机不在总线上，
  **绝不能 return**，否则上层会拿它当「相机还在」的证据。
- `recover()` 里「复位救不了」**不再撒手**：继续往下走一次普通重开
  （节点可能已经被内核自己修好了），开不上再过 6 秒重试。
- `read_bgr()` 的「连续 3 次空帧」加时间判据 `STALE_GRACE_S = 1.5s`：
  12fps 下 3 次空帧只要 0.25 秒，链路抖一下就能凑满 ——
  为这么一下去 close→open（甚至复位整条总线），是自己给自己制造断流。
- 复位成功后冷却从 30 秒降回 6 秒：贵的部分（重新上电、重新枚举）已经付过了。
- `usb_reset_host(..., until=...)`：等总线回来时**一边等一边探**，不再死睡满 9 秒。
- `_usb_resets` **只统计真的动过 sysfs 的复位**。以前 sysfs 里连控制器都没有、
  `usb_reset_host` 什么都没做就返回失败时也 +1 —— 操作页那个「已复位 1536 次」
  就是这么来的（内核侧只重新注册过 87 回）。失败另计 `usb_reset_fails`，
  并在操作页单列一行：>0 就是软件救不回来、要人工插拔。

**受控验证（不是推演）**：`echo 0 > /sys/bus/usb/devices/7-1.1/authorized`
把相机从总线上摘掉（只动相机，不碰 hub 和控制器），每 2 秒读一次 `/api/state`：

| 时刻（注入后） | 读数 |
|---|---|
| +0.0s | `open=True`，开始读到空帧 |
| +2.0s | `open=False`，`fail_streak=9` |
| +6.1s | **`usb_resets=1`** —— 应用自己复位了控制器 |
| +8.1s | **`open=True, reopens=1`**，`seq` 重新开始涨（182 → 194） |

之后连续 80 秒 12fps 稳定、`usb_reset_fails=0`。
即 **~8 秒自愈**，而改之前是「冻住不动，等人去点复位」。

**附带发现（现场查日志用得上）**：这块板子上 `dmesg -T` 的时间戳**比真实时钟快约 25 秒**。
用 `echo t > /dev/kmsg` 标定过：wall 10:05:54 时，dmesg 给那条消息盖的是 10:06:19。
所以**别拿 dmesg 的绝对时间去和应用日志对齐** —— 一次总线复位真实发生在 10:04:08，
dmesg 上写的是 10:04:33。要对齐就用相对间隔，或者自己往 `/dev/kmsg` 打个记号。

**教训**：

- **「设备还在吗」这个判据，必须顺着符号链接看目标。** 悬空链接是掉线之后最常见的
  中间态，而它在字符串层面跟「一切正常」长得一模一样。
- **自愈分支里那句「救不了就算了」，要追问一句：放弃之后还有别的路吗？**
  这里放弃掉的，恰恰是「换句柄」这条最有希望的路。
- **计数器的语义要跟名字对得上。** 「已复位 1536 次」把一件查不出原因的假象，
  变成了操作员眼里的既定事实。
- **别把「读数没涨」当好消息**：`reopens=0` 一度让人以为链路是稳的，
  实际是自愈根本没被触发。

## 坑 40 · handpose 在无人画面凭空"捏"出一只 OK 手（2026-10-09）★

**现象**：手势闸门上线当天做误触发测试 —— 对着**空办公室**连拍 20 帧，
`handpose`（MediaPipe hand_landmark_lite 的 ONNX 导出）**20/20 帧都报出"一只手"**，
置信度 0.54~0.84（远超 HAND_CONF_MIN=0.30），捏合比最低 **0.0219** ——
比真 OK 手势的 0.137 还像 OK。也就是说：只按"捏合比 + 置信度"判 OK，
机器会在**没有人的时候自己开拍**。

**根因不是阈值定错，是缺前置验真**：
handpose 是"单只手近景"模型。喂它一张没有手的图，它不会说"没有手"，
而是**强行把纹理最像手的区域拟合成 21 个关键点**（办公室的椅子、显示器边缘
都能被拟合成手）。置信度帮不上忙 —— 它衡量的是"这套关键点内部自洽"，
不是"这真是只手"。阈值 0.25 当初在 1 正 9 负的官方图集上定的，方向可信，
但**绝对余量从未在真实相机、真实场景下复核过**。

**修法：人形验真闸门**。手的关键点框**中心**必须落在一张真实人形检测框内
（各边按 `BOOTH_GESTURE_PERSON_PAD=0.15` 外扩，容忍举手到头顶/伸到身侧）。
人形框复用既有 yolov8n det（`Booth._person_boxes_for` → `person_boxes_provider`
注入 `GestureClient`），零新增模型。判据用中心点而不是要求手框完全被包含 ——
人形检测框本身就常比真人紧。
修复实测：空场景误报 10/21 → **0/21**；阳性通路另测可用。

**三个必须写下来的配套决定**：

- `person_boxes` 缺省（None/[]/取不到）一律**判阴性** —— 宁可漏检，不可误拍。
  生产路径绝不许绕过 provider 直调 worker。
- 外部 `POST /api/gesture/detect` **不透传** person_boxes：验真人形框由服务端
  自己算（对同一帧跑 det），请求体里的字段被忽略 —— 否则接口就成了"伪造人形框"的后门。
- ` GestureClient` 的 worker **stderr 必须 `DEVNULL`**，不能用 PIPE：PIPE 没有读者，
  worker 的 warning 写满 64KB 缓冲后 worker 阻塞在 stderr 写入上 → 主进程表现为
  回包超时 → kill 重启 → 新进程又写满 → 死循环（见坑 41）。

**现场调参顺序**（先调环境变量，不改代码）：误触发 → 收紧 `BOOTH_GESTURE_PERSON_PAD`
（0.15 → 0.10）；漏检 → 放宽 `BOOTH_GESTURE_PINCH_MAX`（0.25 → 0.30），
并确认人在画面里够大 —— det 检不出人形时手势永远过不了闸（安全侧错误）。

## 坑 41 · worker 的 stderr 用 PIPE 却没人读，队列 tick 被拖到"假死"（2026-10-09）★

**现象**：手势闸门上线后，队列日志从 10:14 起看起来"停摆"—— 半小时没有叫号、
没有手势日志，`journalctl --since` 过滤出来是空的。第一反应：tick 线程死锁。

**排查走过的弯路（都有实测，别重走）**：

- 先怀疑并发 det 抢锁：用 4 线程同时打 `InferWorker.det`，全部 2 秒返回 —— 排除。
- 再怀疑 GIL 饥饿：`preview-hub` 线程只占 9% CPU —— 排除。
- 用线程名定位到 `auto-flow-tick`，看 `/proc/<tid>/wchan` 是 `hrtimer_nanosleep`，
  于是断定"卡死在 sleep 里"。**这个推断是错的** —— sleep(0.5) 是 tick 循环里
  占比最大的状态，用 faulthandler 连续 6 次采样栈全部落在 sleep 行，
  概率上完全正常，根本不能当"卡死"的证据。
- 最终用 faulthandler（SIGUSR1 → dump 到文件）看到 tick 栈**只是 sleep**，
  才意识到：**线程根本没死，是"原因不变时不打日志"的静默策略骗了我们**。

**真正的 bug 在 gesture worker 的 stderr**：`subprocess.Popen(stderr=subprocess.PIPE)`
但主进程只读 stdout、从不读 stderr。onnxruntime/OpenCV 的 warning 写满 64KB
管道缓冲后，worker **阻塞在下一次 stderr 写入**；主进程侧表现为回包超时 →
kill → 重启 → 新 worker 又写满 → 无限循环。tick 每 1.5s 探测一次就撞一次。

**修法**：`gesture_client.py` 的 worker 启动改为 `stderr=subprocess.DEVNULL`
（诊断信息没有保留价值：加载失败走 stdout 哨兵协议的 error 字段带回）。
`infer_client.py` 的 stderr 用 PIPE 是安全的 —— worker 死亡路径上有 `stderr.read()`。

**两条可复用的教训**：

1. **PIPE 是有容量的契约**：给了 PIPE 就必须有人读（或读端就绪），否则子进程
   会在 64KB 处静默挂起。用不上子进程的 stderr，就 DEVNULL。
2. **"没有日志"≠"线程死了"**：防刷屏的静默策略（原因不变不打日志）会让
   正常运行的系统在日志里看起来像停摆。判活要看线程栈（faulthandler dump）
   或心跳计数，别拿日志流当生命信号。
